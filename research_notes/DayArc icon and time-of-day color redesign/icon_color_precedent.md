# Icon Systems and Time-of-Day Colour Treatments on Smartwatch Faces

## Icon implementation approach used by shipped Connect IQ watch faces

### Takeaway
Among Connect IQ developers, the dominant technique for icon-forward watch faces is a **custom icon font** (glyphs baked into a bitmap font resource, drawn with `dc.drawText()` like any other character), not raw PNG bitmaps or hand-drawn vector primitives. The font approach is explicitly favoured because it lets the same icon glyph be recoloured by just changing the text draw color, instead of needing a separate tinted bitmap per colour. `Dc.drawBitmap2()` with the `:tintColor` option (Connect IQ 4.2.1+) is a real, working, and discussed second technique, used when a developer already has the icon in bitmap/PNG form rather than as a font glyph — but it comes with real friction (an easy-to-hit syntax gotcha, and reports of it silently not tinting on some image formats/devices).

### Cited Findings
- On the Garmin Connect IQ developer forum thread "Custom font icon," the recommended production workflow is to design icon glyphs in FontForge (or edit an existing bitmap font's PNG cells directly), convert with a bitmap-font tool (BMFont), and load the result as a normal Connect IQ font resource: "The procedure is not too different from converting a pre-existing font (e.g. TTF) to a bitmap font for use with your Garmin, except that you have to create your own custom font using something like FontForge." — [Garmin Forums: Custom font icon](https://forums.garmin.com/developer/connect-iq/f/discussion/165912/custom-font-icon)
- Same thread: a simpler, very common variant is directly editing an existing bitmap-font's PNG image, then hand-writing the `.fnt` file to map arbitrary characters to icon cells: "probably makes a lot more sense for most use cases, when you already have the icon in bitmap form" — with a practical scheme of using mnemonic characters (e.g. `B`=full battery, `b`=empty battery, `P`=phone connected) and reserving spare slots for future icons. — [Garmin Forums: Custom font icon](https://forums.garmin.com/developer/connect-iq/f/discussion/165912/custom-font-icon)
- On the separate thread "How do you add icons to watch faces?," a developer describes exactly this pattern: "I created a custom font with BMfont, with just a few characters in it. And then modified the .png for those characters to become icons," and states the colour-flexibility rationale directly: "you can also change the color of icons without needing multiple bitmaps." Icons are then drawn with ordinary text calls, e.g. `dc.drawText(x,y,myiconfont,"B",Gfx.TEXT_JUSTIFTY_CENTER)`. — [Garmin Forums: How do you add icons to watch faces?](https://forums.garmin.com/developer/connect-iq/f/discussion/2368/how-do-you-add-icons-to-watch-faces)
- The same thread warns the icon-font PNGs must stay small — oversized source bitmaps cause simulator/device out-of-memory errors — "start really small" with icon dimensions and file size, i.e. this is treated as the standard, memory-safe solution the community converged on. — [Garmin Forums: How do you add icons to watch faces?](https://forums.garmin.com/developer/connect-iq/f/discussion/2368/how-do-you-add-icons-to-watch-faces)
- Crystal Face (warmsound/crystal-face), one of the most widely used third-party Connect IQ watch faces (multi-device-family, actively maintained), ships dedicated per-resolution resource folders including `resources-small-icons/fonts` and `resources-small-time/fonts` — folder naming that indicates icon glyphs are shipped as font resources per screen size/density, consistent with the forum-recommended icon-font pattern rather than a flat bitmap-per-icon layout. (Inference from repo structure; the README itself does not narrate the icon technique in prose.) — [GitHub: warmsound/crystal-face](https://github.com/warmsound/crystal-face)
- `Dc.drawBitmap2()` with `:tintColor` is a real, separately-documented technique developers use specifically to make a single white/greyscale PNG asset themeable, e.g. for "complication icons on a watch face to match a user-defined theme color." Working call shape: `dc.drawBitmap2(CX, CY, bmp, { :transform => transform, :tintColor => 0xFFFFFF });`. — [Garmin Forums: drawBitmap2 and tintColor](https://forums.garmin.com/developer/connect-iq/f/discussion/353151/drawbitmap2-and-tintcolor); [Garmin Forums: How to use drawBitmap2 and tintColor?](https://forums.garmin.com/developer/connect-iq/f/discussion/339318/how-to-use-drawbitmap2-and-tintcolor)
- The recommended source-asset format for tintColor bitmaps is a **greyscale PNG with alpha channel** (the developer in the thread tested both 8-bit and 16-bit variants), declared as a normal foreground-scope bitmap resource, e.g. `<bitmap id="sunriseIcon" filename="png/sunrise6.png" scope="foreground" />`. — [Garmin Forums: How to use drawBitmap2 and tintColor?](https://forums.garmin.com/developer/connect-iq/f/discussion/339318/how-to-use-drawbitmap2-and-tintcolor)
- The technique has a real, easy-to-hit gotcha: passing the option key as a quoted string (`":tintColor"`) instead of a Monkey C symbol (`:tintColor`) silently fails; the fix reported in-thread is simply "Try without the double quotes around :tintColor." Other forum threads ("Are there drawBitmap2 tint/rotate limitations on devices?," "dc.drawBitmap2") report inconsistent results — one developer using RGBA PNGs with white/black/transparent regions found the tint sometimes has no visible effect, and one bug report describes `drawBitmap2` throwing an exception ("Source must be native color format") on certain devices (FR165/FR165m). — [Garmin Forums: How to use drawBitmap2 and tintColor?](https://forums.garmin.com/developer/connect-iq/f/discussion/339318/how-to-use-drawbitmap2-and-tintcolor); [Garmin Forums: Are there drawBitmap2 tint/rotate limitations on devices?](https://forums.garmin.com/developer/connect-iq/f/discussion/354206/are-there-drawbitmap2-tint-rotate-limitations-on-devices); [Garmin Forums: Call to drawBitmap2 causes exception on FR165 and FR165m](https://forums.garmin.com/developer/connect-iq/i/bug-reports/call-to-drawbitmap2-causes-exception-on-fr165-and-fr165m)
- The "how to use drawBitmap2 and tintColor" thread had 1,767 views and 19 subscribers at time of research, which — while not a popularity ranking of faces — indicates this is a frequently-hit, not-niche question among Connect IQ icon developers. — [Garmin Forums: How to use drawBitmap2 and tintColor?](https://forums.garmin.com/developer/connect-iq/f/discussion/339318/how-to-use-drawbitmap2-and-tintcolor)
- No forum or GitHub source found in this research describes hand-drawn vector primitives (`fillPolygon`, `drawArc`, etc.) as a mainstream icon technique for weather/battery/calendar-style glyphs specifically; vector primitives came up only for simple geometric elements (arcs/meters/hands), not iconography, in the sources reviewed.

### Inferences
- For DayArc's stated icon types (weather-condition, Body Battery-adjacent, calendar/event glyphs), the icon-font approach is the better fit on both axes the studio already cares about: it's the community-converged, memory-safe, low-complexity path, and it directly solves "colour that can change per time-of-day window" for free — a glyph drawn via `dc.drawText()` inherits whatever `setColor()` is active, exactly like the existing plain-text hero read, so the per-window accent-colour mechanism DayArc already has for text can extend to icons with no new colour-application code path.
- `drawBitmap2` + `:tintColor` is a viable *fallback* only for icon shapes that are hard to render as font glyphs at the target size (e.g. an image with genuine shading/detail); given the documented gotchas (symbol-vs-string syntax trap, inconsistent tint behaviour, one confirmed device-specific exception), it is the higher-risk path for an icon-forward face and would need per-device testing (device testing is already a known gap per studio house rules).

### Gaps
- Could not find a direct statement from Garmin itself (developer docs or blog) on which technique Garmin's own native watch faces/glances (Body Battery glance, weather glance) use internally — Garmin does not appear to publish source for first-party faces/glances, and no forum post was found reverse-engineering this. The Body Battery glance icon is described only visually (a person silhouette with a lightning bolt / gauge) in the Garmin owner's manual, with no implementation detail. — [Garmin Support: Body Battery Glance](https://www8.garmin.com/manuals/webhelp/GUID-0221611A-992D-495E-8DED-1DD448F7A066/EN-US/GUID-28BA6B01-9460-4FF3-8499-5D91269FD50B.html)
- Did not find r/GarminWatches or r/connectiq Reddit threads with substantive icon-technique discussion beyond what the Garmin forums already covered; search results for that combination returned no distinct new content, so this sub-source is effectively empty for this question.

## Time-of-day colour-shift precedent for icon/glyph elements (vs. value-based "verdict" colour)

### Takeaway
Time-of-day/daypart-driven accent colour (colour-by-context) is a real, shipped pattern — clearest on Apple Watch's Solar-family faces (background/sky colour, not icon colour) and on third-party Wear OS/Android faces like "Watch Face – Minimal & Elegant," which has an explicit "Colors Scheduler" that recolours the whole face **purely on a time schedule**, decoupled from any live data. Value-based colour ("verdict" colour, banned in this studio) is also a real, shipped pattern on the opposite end — a Pixel Watch custom face maps heart-rate/stress *value* to a mood-ring-style colour gradient — and it is well received by its own audience, which is exactly the trap: it "works" for early adopters while being the pattern this studio has ruled out for DayArc. No source found blurs the line at the level of icon glyphs specifically (icon-hue-by-value); the found examples are whole-face-background colour, not per-icon colour, in both directions.

### Cited Findings
- Apple Watch's **Solar Dial** face changes its background sky colour continuously across the day (dark to light and back), including a "transition from blue, to a deeper blue, to a lovely pale pink" during twilight — driven by actual solar position/time, not a live biometric value: "The background color differs between daytime from sunrise to sunset and nighttime, so you can intuitively understand the length of the day." This is colour-by-time-context, applied to background/sky, not to an icon or complication glyph. — [MacStories: The Beauty of the Apple Watch's Solar Dial Face](https://www.macstories.net/linked/the-beauty-of-the-apple-watchs-solar-dial-face/)
- Apple Watch's **Solar Analog** face uses "light and shadows that shift throughout the day in response to the position of the sun" — again a time/astronomical-position-driven visual change, not a data-value-driven one. — [Apple Support: Apple Watch faces and their features](https://support.apple.com/guide/watch/faces-and-features-apde9218b440/watchos)
- Apple Watch's **Palette** face "displays the time using three overlapping layers of colors that shift throughout the day" — a third Apple example of colour tied to time-of-day rather than to any measured value. — [Apple Support: Apple Watch faces and their features](https://support.apple.com/guide/watch/faces-and-features-apde9218b440/watchos)
- Third-party Wear OS/Android face **"Watch Face – Minimal & Elegant"** ships a dedicated **"Colors Scheduler"** feature, described directly by its developer: "The color scheduler allows you to change the colors of the faces based on the time context. There is no need for 3rd party apps like Tasker. It works on its own." This is a named, explicit, purely time-driven (not value-driven) colour-scheduling feature on a real shipped face, closely analogous to what DayArc wants for its four fixed windows. — [XDA Developers: Minimal & Elegant Watch Face with Tasker integration](https://www.xda-developers.com/minimal-elegant-watch-face-with-tasker-integration-giveaway/)
- On the opposite (banned) end: a custom Pixel Watch face reported by How-To Geek uses a **continuously shifting gradient background tied to heart-rate/stress value**, built around "four zones with specific BPM ranges" where higher heart rate produces "warmer, more intense colors (suggesting stress)" and lower heart rate produces "cooler greens and blues" — an explicit digital mood-ring / verdict pattern. The author states it "does exactly what I wanted" and that "the gradient colors are more effective" than raw numbers for quick assessment; a commenter called it "a pretty neat watch face." No negative reception was reported in this source. — [How-To Geek: My Pixel Watch now shows my stress level like a mood ring](https://www.howtogeek.com/my-pixel-watch-now-shows-my-stress-level-like-a-mood-ring/)
- That same How-To Geek piece traces the "mood ring" colour logic to the original 1970s liquid-crystal mood rings, where skin temperature drove colour ("stressed" = red/purple, "calm" = green/blue) — the digital face is a direct value-to-colour-verdict translation of that logic, using heart rate as the input variable instead of skin temperature. — [How-To Geek: My Pixel Watch now shows my stress level like a mood ring](https://www.howtogeek.com/my-pixel-watch-now-shows-my-stress-level-like-a-mood-ring/)
- Loosely adjacent, non-watch-face precedent for *not* letting a single accent colour carry two meanings at once: a hobbyist clock-face project's design-review PR explicitly avoids assigning a colour ("red") to a face's identity that the app's UI already uses to mean something else ("on a break," a status signal), with the stated principle "the colour is the face's character rather than a match of its paint." This isn't a shipped smartwatch face (it's a personal desktop/clock-style app, not a Garmin/Apple/Wear OS product) and doesn't concern time-of-day, but it is a directly-sourced articulation of the same "don't let one hue channel double as both a mode signal and a value signal" concern DayArc is applying to icons. Flagged clearly as a tangential, non-watch-face source. — [GitHub PR: niclaslindstedt/time #33](https://github.com/niclaslindstedt/time/pull/33)
- A Garmin Connect IQ forum thread ("Implementing Multiple Watchface Themes with Configurable Colors") confirms developer interest in configurable/switchable theme colour on Connect IQ faces, but the search summary available did not surface any specific *automatic, time-of-day-driven* colour-switching Connect IQ face by name — theme switching discussed there appears to be user-selected, not daypart-automatic. — [Garmin Forums: Implementing Multiple Watchface Themes with Configurable Colors](https://forums.garmin.com/developer/connect-iq/f/discussion/378564/implementing-multiple-watchface-themes-with-configurable-colors)

### Inferences
- None of the sourced examples change an *icon's* hue independent of the rest of the face by time-of-day or by value — every found example (Apple Solar/Palette, Minimal & Elegant, the Pixel Watch mood-ring face) recolours the whole face/background, not a single glyph. DayArc's proposal (per-window accent shift applied consistently to text *and* icon, never per-reading) has no exact shipped precedent either way, for better or worse — it is not contradicted by any found example, but it is also not directly validated by one at the icon-only granularity. This is inference, not a sourced claim.
- The Pixel Watch mood-ring example is useful specifically as the "here is what the banned pattern looks like when someone ships it and likes it" reference: it is not an edge case that got backlash, it's presented as a personal success by its own creator — which supports treating "value-based colour verdict" as a real temptation/precedent that has to be actively designed against, not a hypothetical strawman.

### Gaps
- Could not find any well-reviewed or store-ranked Wear OS/Apple/Garmin face (as opposed to a single hobbyist DIY Pixel Watch face) that ships value-based icon or accent colour and has documented store reviews/complaints specifically about that colour choice; the one clear "blurred line" example found (Pixel Watch mood ring) is a single enthusiast's custom face (via a watch-face-builder tool), not a widely distributed/reviewed product, so "how it was received" beyond one article's comment section could not be sourced.
- Could not find Wear OS's own official design-guidance language (Wear OS Tiles/watch-face guidelines beyond what's already given as background) explicitly endorsing or discussing time-of-day accent colour as a named pattern; the "Minimal & Elegant" and Apple examples are product-level, not platform-guidance-level, evidence.

## Weather condition iconography conventions at small size

### Takeaway
The three cited weather-icon systems converge on the same idea for small/monochrome contexts: a **thin-stroke, outline-only ("line") variant, kept simple enough to read as a silhouette**, is the version each system recommends or provides specifically for small sizes and single-colour/tinted contexts — directly relevant to DayArc's ~24–40px round-face constraint.

### Cited Findings
- **Meteocons** ships four explicit style variants — Fill (rich gradients/illustrative), Flat (solid colour), Line (outline-based), and Monochrome (single colour) — documented per-style, each "meticulously crafted in every variant," on a 128×128 base design canvas. — [Meteocons: Getting Started](https://meteocons.com/docs/getting-started/); [Meteocons](https://meteocons.com/)
- Meteocons' own documentation recommends the **Line style specifically for small sizes**: "Best for minimal interfaces, small sizes," described as "outline only, thin strokes." — [Meteocons: Getting Started](https://meteocons.com/docs/getting-started/)
- Meteocons' **Monochrome style is built for tinted/themed use**: it "uses `currentColor`, so the icons automatically match your text color. This makes it ideal for dark mode or themed interfaces" — i.e., designed to be recoloured by the surrounding UI's colour, the same mechanism DayArc would want for a tintColor- or drawText-driven icon on a colour-shifting face. — [Meteocons: Getting Started](https://meteocons.com/docs/getting-started/)
- **Google Material weather icons** are offered in both **Filled and Outlined** styles as 48×48 SVGs with light/dark theme variants, following Material Symbols' general design-axis system (Optical Size 20–48px, Weight 100–700, Grade -50 to 200, Fill 0–100) that lets one glyph family scale and reweight for different contexts/sizes rather than needing bespoke icons per size. Material's Outlined style specifically uses square (non-rounded) interior corners as a style rule. — [Google Fonts: Material Symbols guide](https://developers.google.com/fonts/docs/material_symbols); [GitHub: mrdarrengriffin/google-weather-icons](https://github.com/mrdarrengriffin/google-weather-icons)
- **Apple's weather glyphs** are part of the SF Symbols system, which is explicitly built for cross-size, cross-weight legibility: SF Symbols "integrate seamlessly with the San Francisco system font, automatically aligning with text in all weights and sizes," and Apple's own current-conditions symbol set is documented at the API level (`WeatherKit.CurrentWeather.symbolName`) as a fixed, named glyph per condition — implying a controlled, monochrome-friendly glyph set designed to sit inline with text rather than as full-colour illustrations. — [Apple Developer: SF Symbols (HIG)](https://developer.apple.com/design/human-interface-guidelines/sf-symbols); [Apple Developer: symbolName — WeatherKit.CurrentWeather](https://developer.apple.com/documentation/weatherkit/currentweather/symbolname)

### Inferences
- The consistent pattern across all three systems — a distinct thin-stroke/outline or single-colour glyph variant, purpose-built for small size and tint-by-surrounding-colour — maps directly onto what DayArc needs for its weather glyph at MIP/64-colour, ~24–40px scale: a single-weight outline (not filled illustrative) glyph, recoloured via the same mechanism (drawText colour or tintColor) already used for the rest of the per-window accent, rather than a multi-colour illustrative icon.
- None of the three systems' filled/illustrative/gradient variants (Meteocons "Fill," Material "Filled") are good candidates for a 64-colour, small-size, single-accent-hue watch face — they're designed for larger, full-colour-capable surfaces — so if DayArc licenses or references any of these sets for shape language, the outline/line/monochrome variant is the only one structurally compatible with the existing hardware constraint already established in prior research.

### Gaps
- Could not retrieve Material Design 3's full icon-design guidance page content (the fetch returned only the page title, no body text) — so exact Material stroke-weight-in-px or minimum-size recommendations could not be confirmed beyond the design-axis ranges found via secondary sources (Google Fonts developer docs). Flagged as an unconfirmed gap rather than inferred.
- Could not find a direct, named statement from Apple listing a stroke-weight-in-points spec for weather SF Symbols at Watch complication sizes specifically (vs. general SF Symbols HIG); the legibility-at-small-size claim for SF Symbols is inferred from the general "integrates with San Francisco font at all weights and sizes" design goal, not a weather-specific spec sheet.
