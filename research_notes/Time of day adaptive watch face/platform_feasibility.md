# Connect IQ Platform Feasibility — Time-of-Day Adaptive Watch Face + Widget

## Does Toybox.Weather give current temp, precipitation, UV, wind, sunrise/sunset without extra app-side permissions? Refresh cadence and phone-sync dependency?

### Takeaway
`Toybox.Weather` exposes temperature, precipitation chance, UV index, wind speed/bearing, and (on API 3.3.0+, device-limited) sunrise/sunset, all from a **device-side cache** with no manifest permission required for the weather fields themselves — but the API never triggers a fetch; it only reads whatever was last synced to the device, so freshness depends entirely on phone/GPS-linked sync the app can't control. `observationLocationPosition`/`observationLocationName` specifically require the `Positioning` permission.

### Cited Findings
- `Weather.getCurrentConditions()` "returns the most recently cached weather conditions" as a `Weather.CurrentConditions` object or `null`; no fetch-on-demand call exists in the module — [Toybox.Weather](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html)
- `CurrentConditions` fields confirmed present: `temperature` (°C), `feelsLikeTemperature` (°C), `highTemperature`/`lowTemperature` (°C), `condition` (enum), `windSpeed` (m/s), `windBearing` (degrees), `relativeHumidity` (%), `precipitationChance` (%), `pressure` (Pa), `uvIndex` (0–10), `visibility` (m), `cloudCover` (%), `dewPoint` (°C), `observationTime` (UTC `Time.Moment`) — [Toybox.Weather.CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- `observationLocationPosition` and the deprecated `observationLocationName` require the position permission to be non-null; other fields are not gated on a permission in the class doc — [Toybox.Weather.CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- Minimum API Level for `getCurrentConditions()`/`getHourlyForecast()`/`getDailyForecast()` is 3.2.0; `getSunrise()`/`getSunset()` (which take explicit location + date params rather than reading current conditions) require API 3.3.0 and have "more limited device support" — [Toybox.Weather](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html)
- All `CurrentConditions` fields "may return null" — [Toybox.Weather.CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- App-review-relevant battery guidance elsewhere on the dev portal states "frequent weather updates ... can reduce battery life," implying weather refresh has a device-managed, not app-managed, cadence and cost — [Connect IQ App Review Guidelines listing, via search snippet](https://developer.garmin.com/connect-iq/app-review-guidelines/) (snippet only; page itself did not render for direct fetch — see Gaps)

### Inferences
- Because there is no app-triggered "refresh now" call, a morning dress-for-weather feature is inherently dependent on whatever sync cadence Garmin Connect Mobile / the device's own weather-sync schedule already runs (commonly hourly-ish on synced devices, GPS-assisted on some models) — the app can only read the last cache, never force a fresh pull.
- No manifest permission entry is needed to read temperature/precip/UV/wind values; `Positioning` permission is only needed if the app also wants the observation location itself (not needed for the values used in dress-for-weather logic).

### Gaps
- The exact refresh cadence (e.g., "every 60 minutes," "on phone Bluetooth reconnect only," "GPS-fix triggered") is not documented on the API reference pages reachable via fetch; the Weather module doc does not state a sync interval. This would need either a Garmin forum statement from a Garmin employee or empirical device logging — not found in this pass.
- Could not confirm whether weather sync happens without a paired phone at all (e.g., via built-in LTE/Wi-Fi on models that have it) versus strictly requiring Garmin Connect Mobile relay — the `core-topics` pages (Positioning, Backgrounding) that likely address this returned only navigation-menu content when fetched (JS-rendered SPA not captured by the fetch tool), so this remains unverified from a primary source in this pass.

## Is there a native Connect IQ API for calendar/next-event data, or does it require a companion app / phone-side push? What's the realistic feasible approach for "next event starts/ends" on-device?

### Takeaway
There is **no native calendar/agenda API** in Connect IQ. The only realistic on-device path is a companion (phone-side) app pushing next-event data to the watch via `Toybox.Communications` phone-app messaging (foreground and, per forum confirmation, also background-eligible), landing in a **widget or device app** — not a watch face, since watch faces cannot use Communications at all.

### Cited Findings
- "If you want to get calendar data from a phone, you can't do it from a Connect IQ watchface, as no communication is allowed in a watch face. However, you could do it in a widget or watch-app." — [Garmin Forums: Calendar API discussion](https://forums.garmin.com/developer/connect-iq/f/app-ideas/280141/calendar-api)
- The community request thread frames a native calendar API as a standing **feature request**, not a shipped capability: "it would be great if the agenda items on the device would be readable through a Calendar API" — [Garmin Forums: Calendar API](https://forums.garmin.com/developer/connect-iq/f/app-ideas/280141/calendar-api)
- Connect IQ data fields (the in-activity metric type) "can't get data from a phone either" — same thread — [Garmin Forums: Calendar API](https://forums.garmin.com/developer/connect-iq/f/app-ideas/280141/calendar-api)
- `registerForPhoneAppMessages()` / `transmit()` in `Toybox.Communications` let a watch app exchange messages with a companion phone app; this messaging is usable "not just in foreground apps but also in background services" per forum discussion of the Background module — [Garmin Forums: Background module - companion app communication](https://forums.garmin.com/developer/connect-iq/f/discussion/6168/background-module---is-companion-app-communication-supported-in-the-background); class reference: [Toybox.Communications.PhoneAppMessage](https://developer.garmin.com/connect-iq/api-docs/Toybox/Communications/PhoneAppMessage.html)
- Garmin's own "Glance" showcase app is exactly this pattern: a widget paired with an Android companion app pushing dashboard data to the watch — [Garmin Forums: Glance showcase](https://forums.garmin.com/developer/connect-iq/f/showcase/6160/glance---phone-dashboard-widget-with-android-companion-app/40784)
- Background services can also be driven by scheduled **temporal events** (time-based, not just phone-push), but a temporal event alone cannot manufacture calendar data — it can only poll/read whatever the companion has already deposited in app storage, and is throttled to no more than one temporal event per 5 minutes per app (see Background section below) — [Garmin Forums: Background => Temporal Event](https://forums.garmin.com/developer/connect-iq/f/discussion/5443/background-temporal-event)

### Inferences
- The realistic feasible architecture for "next event starts/ends" is: **widget (or device app), not a watch face**, receiving push messages from a phone-side companion app (which reads the OS calendar), storing the next-event payload in `Application.Storage`/property storage, and a temporal-event-driven background service (subject to the 5-minute floor) refreshing the on-screen countdown/label between pushes.
- Because watch faces are explicitly barred from Communications, a "next event" glance cannot live directly on the always-visible watch face complication slot unless it's read from Garmin's own Complications system fed by a value the widget/companion already wrote to shared storage — and Complications' data-source model for third-party custom values was not confirmed as feasible in this pass (see Gaps below and the Complications question is out of scope of the listed key questions but adjacent).

### Gaps
- Whether a widget can then republish that pushed data into a native Complication slot (so it *appears* on the watch face itself) was not confirmed — the `Toybox.Complications` core-topics page and API pages describe complications as read access to Garmin's own built-in metrics (steps, HR, Body Battery, etc. — see `Complications.getComplication(id)`, `Complications.Iterator`) with a subscribe/callback model; no primary-source text was retrieved confirming or denying whether a third-party app can register itself as a **complication data provider** with custom data (e.g., "next event"). This needs a direct read of `developer.garmin.com/connect-iq/core-topics/complications/`, which did not render through the fetch tool in this pass (JS-rendered page, only nav returned).
- No data on typical push latency/reliability of phone→watch Communications messaging for this use case.

## What does Toybox.ActivityMonitor / Toybox.SensorHistory expose for stress score and Body Battery — refresh rate, and which device generations/API levels support each?

### Takeaway
Stress score is exposed as a live snapshot via `ActivityMonitor.Info.stressScore` (API 5.0.0+, narrow device list) and as history via `SensorHistory.getStressHistory()` (API 3.3.0+, broader device list); Body Battery is **history-only** — there is no live Body Battery field in `ActivityMonitor.Info`, only `SensorHistory.getBodyBatteryHistory()` (API 3.3.0+). Neither API documents a fixed sample interval; both are stated as device-dependent.

### Cited Findings
- `ActivityMonitor.Info.stressScore`: `Number` or `null`, 0–100 scale (0–25 Resting, 26–50 Low, 51–75 Medium, 76–100 High), "calculated using a rolling average of the last 30 seconds of stress level readings," minimum API level 5.0.0, device support limited to newer models such as fēnix 7 series+, Forerunner 165+, Venu 2+ — [Toybox.ActivityMonitor.Info](https://developer.garmin.com/connect-iq/api-docs/Toybox/ActivityMonitor/Info.html)
- **Body Battery is not present as a field in `ActivityMonitor.Info`** — confirmed absent from that class's documented fields — [Toybox.ActivityMonitor.Info](https://developer.garmin.com/connect-iq/api-docs/Toybox/ActivityMonitor/Info.html)
- `SensorHistory.getBodyBatteryHistory()` returns a `SensorHistoryIterator` of 0–100 samples ("0 indicates the body is drained ... 100 indicates the body is rested and charged"); minimum API level 3.3.0; "the time between each SensorSample in the iterator may be device dependent" (no fixed interval documented); "this function always returns the most recent sensor history samples" (no stated poll/refresh frequency); supported on ~90+ devices including fēnix 6+, Forerunner 245+, Venu series, Instinct series — [Toybox.SensorHistory](https://developer.garmin.com/connect-iq/api-docs/Toybox/SensorHistory.html)
- `SensorHistory.getStressHistory()` returns 0–100 samples (higher = more stress); minimum API level 3.3.0; device-dependent sample interval, ~80+ devices supported, excluding some older fēnix/Forerunner models that support Body Battery — [Toybox.SensorHistory](https://developer.garmin.com/connect-iq/api-docs/Toybox/SensorHistory.html)
- A known SDK bug was reported: "oldest and newest sample time of the body battery and stress iterator are not properly initialized" — relevant if the spec relies on precise sample timestamps — [Garmin Forums bug report](https://forums.garmin.com/developer/connect-iq/i/bug-reports/oldest-and-newest-sample-time-of-the-body-battery-and-stress-iterator-are-not-properly-initialized)
- Community/DC Rainmaker coverage corroborates that stress, Body Battery, and remaining recovery time access were added to the Connect IQ API as part of platform updates — [DC Rainmaker: Garmin's Connect IQ Platform Updates](https://www.dcrainmaker.com/2021/10/garmins-connect-platform.html)

### Inferences
- An evening Body Battery summary must be built from `SensorHistory.getBodyBatteryHistory()` (history/graph-style iterator), not from a single live "current Body Battery" field — there isn't one in the public API.
- A midday stress-based "reset nudge" feature should design for the two-tier device reality: `ActivityMonitor.Info.stressScore` (live number, API 5.0.0, newest devices only) is the higher-quality signal where available, with `SensorHistory.getStressHistory()` (API 3.3.0, wider support) as the fallback/backstop for older-but-still-common devices (this matters directly for the target device, Forerunner 965, which needs to be checked against both device-support lists).
- `timeToRecovery` (hours, API 3.3.0, broad device support back to fēnix 5 Plus) is a documented, easy-to-reach adjacent field that could support an evening summary alongside Body Battery.

### Gaps
- No documented numeric sample interval (e.g., "every 15 minutes," "every 2 minutes") for either stress or Body Battery sensor history was found in the API reference; Garmin explicitly states it is device-dependent and undocumented at the value level. Confirming actual real-world interval for the Forerunner 965 specifically would require either a forum statement or empirical on-device logging — not obtained in this pass.
- Did not confirm the exact minimum API level / firmware version installed on Forerunner 965 to know which of `stressScore` (5.0.0) vs. history-only fallback applies; this is a device-lookup task against Garmin's Compatible Devices matrix, not completed here.

## Background Service / temporal-event update budget per device tier, and battery effect of switching content mode several times a day (esp. AMOLED always-on)?

### Takeaway
Connect IQ enforces one hard, documented, cross-device-tier rule: **a given app can run no more than one temporal (time-driven) background event per 5 minutes**, confirmed by a Garmin staff reply on the developer forum, with no stated exception for AMOLED vs. MIP or for user interaction. No AMOLED-specific *background service* budget (separate from the general 5-minute floor) or quantified battery-cost-per-mode-switch figure was found in official documentation in this pass.

### Cited Findings
- "Applications can never run more than one Temporal event of any type within 5 minutes of the last one that ran for that application, no exceptions." "The user's interaction with your widget does not change this restriction." A Garmin representative, replying in the same thread, confirmed: "The design does limit this use case, and there are not any plans to change the limitation at this time." — [Garmin Forums: Background => Temporal Event](https://forums.garmin.com/developer/connect-iq/f/discussion/5443/background-temporal-event)
- Background events can also be triggered by non-temporal system events (e.g., activity goal met) in addition to scheduled temporal events — [Toybox.Background module description, via search snippet](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html) (page itself did not render through fetch — see Gaps)
- General battery guidance from the dev portal (found via search snippet, not confirmed by direct fetch): "complex watch faces, frequent weather updates, always-on seconds, maps, and background connections can reduce battery life" — attributed to Garmin's own developer site content but **not independently verified by a direct page fetch in this pass**; treat as directionally credible but unconfirmed wording.

### Inferences
- A time-of-day adaptive design that wants to change watch-face/widget content mode "several times a day" (morning → midday → evening) is well within the 5-minute floor (transitions are hours apart, not sub-5-minute), so the temporal-event budget itself is not a binding constraint for this specific feature's cadence.
- The 5-minute floor does mean the design cannot rely on background service for fine-grained "next event in N minutes" countdown ticking; the on-screen tick for something like a break/walk nudge would need to be computed from a stored target timestamp and rendered by the normal `onUpdate()`/`onPartialUpdate()` draw cycle (which runs on the device's own display-refresh schedule), not driven by repeated background wakes.
- No official, quantified "battery cost of N content-mode switches per day" figure was located; this appears to be an area where only empirical device testing (per the project's own house rule that "simulator passing is not device proof") can produce a real number for the Forerunner 965.

### Gaps
- Could not confirm whether the 5-minute floor differs at all between full-color low-power ("always-on/AOD") AMOLED behavior and non-AMOLED MIP behavior — the forum thread and module docs describe the limit as universal, but no source was found explicitly stating "and this is identical across AMOLED and MIP tiers" versus simply never addressing the distinction.
- Could not retrieve the full text of `developer.garmin.com/connect-iq/core-topics/backgrounding/` or the "How Do I Create a Connect IQ Background Service" FAQ page — both returned only site navigation when fetched (JS-rendered pages not captured by the available fetch tool), so any additional device-tier nuance those pages might contain (they are the canonical source for this topic) is unverified in this pass. A follow-up pass with a JS-capable fetch or manual browse of those two URLs is recommended before finalizing a spec.
- No official quantified battery-drain number for AMOLED always-on mode generally, or for repeated draw-mode switching specifically, was found from Garmin. Any such figure in circulation should be treated as third-party estimate, not vendor-documented.

## Verify the "no pixel fully lit for more than ~4 minutes continuous" AMOLED burn-in guidance — documented Garmin constraint, community rule of thumb, or unverifiable?

### Takeaway
**This is a community rule of thumb, not a documented Garmin developer-portal constraint** — and the commonly repeated figure in Connect IQ developer forum discussions is **3 minutes**, not 4. No official Garmin developer documentation page was found (in this pass) that states any specific numeric time limit; the two numbers that recur in forum discussion are "no more than 10% of pixels on at once" and "no single pixel on for more than ~3 minutes," both sourced to developer-forum discussion threads rather than a citable Garmin spec page.

### Cited Findings
- Garmin Forums thread on AMOLED always-on/sleep-mode rules: "The rules of no more than 10% of pixels on and no pixel on for more than 1 minute apply to AMOLED watches" for older devices; a forum participant separately states "the max of a single pixel being on for more than 3 minutes is what changed for the Venu 2," and notes the rule "may not be used for some devices" — i.e., forum participants themselves disagree on the exact figure and its device scope — [Garmin Forums: Always on display (sleep mode) behaviour and rules on newer AMOLED watches](https://forums.garmin.com/developer/connect-iq/f/discussion/322419/always-on-display-sleep-mode-behaviour-and-rules-on-newer-amoled-watches)
- Same thread: "if you have any graphic element 2 pixels or more wide or tall ... then a 1 pixel shift in 2 directions is not enough to avoid breaking the 3 minute rule" — again framed as forum tribal knowledge, not a quoted spec — [Garmin Forums: 322419](https://forums.garmin.com/developer/connect-iq/f/discussion/322419/always-on-display-sleep-mode-behaviour-and-rules-on-newer-amoled-watches)
- One commenter in that thread claims to reference "the developer.garmin.com watch faces documentation" as the source, but the specific excerpt is not quoted in the retrievable thread content, and direct fetch of the corresponding official FAQ page (`how-do-i-make-a-watch-face-for-amoled-products`) returned only site navigation, not the article body — so this claimed citation could **not be independently verified** in this pass — [Garmin Forums: 322419](https://forums.garmin.com/developer/connect-iq/f/discussion/322419/always-on-display-sleep-mode-behaviour-and-rules-on-newer-amoled-watches); [FAQ page fetch attempt](https://developer.garmin.com/connect-iq/connect-iq-faq/how-do-i-make-a-watch-face-for-amoled-products/) (nav-only render)
- Garmin's own official position on burn-in, per its device owner's manuals, is that it is expected AMOLED behavior rather than a defect: manuals for vívoactive 6, Venu, Forerunner 265, epix Gen 2, and D2 Air all contain an "About the AMOLED Display" section — [Garmin manuals, e.g. Venu](https://www8.garmin.com/manuals/webhelp/venu/EN-US/GUID-8ECEF6B4-5257-44E9-BB09-778836BBF700.html); a Garmin forum reply elsewhere is paraphrased as stating "burn-in is normal screen behaviour for AMOLED devices" (paraphrase from search synthesis, exact quote not independently re-verified against the manual text in this pass)
- A checked third-party burn-in article (luxelion.com) that search-engine synthesis had attributed the "10%/4-minute" figure to was fetched directly and **does not contain that claim at all** — the specific "4 minutes" number could not be traced to any retrievable source, official or community, in this research pass — [luxelion.com fetch result, this pass]
- No number resembling "4 minutes" appears in any of the primary forum threads or official pages retrieved; the closest documented community figures are 1 minute (original Venu, per forum recollection) and 3 minutes (Venu 2 era, per forum recollection) — [Garmin Forums: 322419](https://forums.garmin.com/developer/connect-iq/f/discussion/322419/always-on-display-sleep-mode-behaviour-and-rules-on-newer-amoled-watches)

### Inferences
- The "~4 minutes" figure the product-spec side has been carrying appears to be an imprecise recollection of the "~3 minute" figure that circulates in Connect IQ developer forums — treat the underlying constraint as real (AMOLED devices do enforce some form of forced-dim/blackout behavior in always-on mode to protect the panel) but treat the specific number as **unverified and likely off by one**, and do not cite "4 minutes" as a Garmin fact in the product spec.
- Regardless of the exact minute count, the actionable design constraint is directionally solid and repeated across multiple independent forum threads: keep static/high-contrast elements small, keep total lit-pixel coverage low in always-on mode, and pixel-shift anything wide/tall — this is safe to carry into a design spec as "best-practice guidance from the developer community," explicitly labeled as such rather than as an official spec.

### Gaps
- No official Garmin developer-portal page stating a specific numeric burn-in time threshold was located or successfully fetched in this pass. The two candidate canonical pages — `connect-iq/connect-iq-faq/how-do-i-make-a-watch-face-for-amoled-products/` and `connect-iq/core-topics/` (watch face / AMOLED sections) — both rendered as navigation-only when fetched with the available tool (JS-heavy SPA), so their body text is unverified here. **This should be treated as an open item**: someone should open those two URLs in a real browser (or a JS-capable fetch) before the spec asserts any specific number, official or otherwise.
- Whether the AOD/burn-in-protection behavior is OS-enforced (device firmware forces dim/blackout regardless of app) versus something the app is merely advised to self-limit was not conclusively separated in the sources retrieved; forum text suggests both framings exist ("exceeding 10% causes the display to go black" implies OS enforcement) but this needs the same primary-source page confirmation as above.

## Connect IQ permission requirements or store-review implications tied to background service / sensor access / weather?

### Takeaway
Weather field access (temperature, precip, UV, wind) requires **no manifest permission**; only the location fields on `CurrentConditions` require `Positioning`. Background services and sensor/`SensorHistory` access are governed by the general manifest permission system and Garmin's App Review Guidelines, but the actual guideline text (battery-impact review criteria, background-service review checklist) could not be retrieved as body text in this pass — the review-guidelines and manifest-and-permissions pages both rendered as navigation shells only.

### Cited Findings
- `Positioning` permission is required specifically for `Weather.CurrentConditions.observationLocationPosition` / `observationLocationName`; other weather value fields (temp, precip, UV, wind, humidity, etc.) are not gated by a stated permission in the class doc — [Toybox.Weather.CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- Garmin publishes a dedicated "Manifest File and Permissions" core-topics page and a separate "App Review Guidelines" page, both of which are the canonical sources for this question, but both returned only site-navigation content when fetched with the available tool in this pass (no article body captured) — [Manifest and Permissions](https://developer.garmin.com/connect-iq/core-topics/manifest-and-permissions/); [App Review Guidelines](https://developer.garmin.com/connect-iq/app-review-guidelines/)
- Garmin Customer Support maintains a consumer-facing FAQ specifically titled "Permissions for Connect IQ Applications," confirming permissions are a user-visible/consent-relevant concept at install time, not just a manifest formality — [Garmin Support: Permissions for Connect IQ Applications](https://support.garmin.com/en-US/?faq=Z8zVsJfH3v1KAhrFTNmZi8)
- Communications (phone-app messaging, used for the calendar/next-event approach) is subject to its own permission problems reported by developers, per forum discussion title "Permissions problem using Toybox.Communications," indicating this permission area is a live pain point worth testing early rather than assuming — [Garmin Forums: Permissions problem using Toybox.Communications](https://forums.garmin.com/developer/connect-iq/f/discussion/260809/permissions-problem-using-toybox-communications)
- General battery-impact guidance surfaced via search snippet (not independently confirmed by direct fetch): background connections and frequent weather updates are called out as things that "can reduce battery life," suggesting Garmin's review process is sensitive to background/weather usage patterns during submission review, but the exact review checklist criteria are unconfirmed — [App Review Guidelines, via search snippet only]

### Inferences
- For the product spec: budget explicit manifest permission review for `Positioning` (only if location-name/observation-location is used — likely skippable if the app just reads temp/precip/UV/wind) and for `Communications` (needed for the companion-app next-event push design) plus whatever sensor permission gates `ActivityMonitor`/`SensorHistory` (these are typically permission-free for on-device stress/Body Battery reads since they're first-party health data already on the watch, but this should be spot-checked against the manifest doc directly rather than assumed).
- Given forum-reported friction with Communications permissions specifically, the calendar/next-event feature (which depends on Communications) carries more store-review and runtime-permission risk than the weather or Body Battery features, and should get device-testing priority.

### Gaps
- Full text of Garmin's official Manifest and Permissions page and App Review Guidelines page was not retrieved — both are JS-rendered pages that the available fetch tool could not extract past the navigation shell. This is the single most important follow-up before finalizing a spec: someone needs to open both pages directly (browser) and extract (a) the full permission list with per-API mapping, and (b) any explicit review criteria mentioning background services, sensor polling frequency, or battery-impact thresholds.
- No confirmation of whether `ActivityMonitor.Info.stressScore` / `SensorHistory` body-battery/stress access requires any manifest permission at all (plausible it's permission-free as first-party on-device data, but not confirmed from a permissions-specific primary source in this pass).
