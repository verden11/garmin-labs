# Connect IQ Platform Feasibility — Time-of-Day Adaptive Watch Face + Widget

## Does Toybox.Weather give current temp, precipitation, UV, wind, sunrise/sunset without extra app-side permissions? Refresh cadence and phone-sync dependency?

### Takeaway
`Toybox.Weather` exposes temperature, precipitation chance, UV index, wind speed/bearing, and (API 3.3.0+, device-limited) sunrise/sunset, all from **device-side cache**. No manifest permission for weather fields themselves. API never triggers fetch; reads only last-synced data -> freshness depends on phone/GPS-linked sync app can't control. `observationLocationPosition`/`observationLocationName` require `Positioning` permission.

### Cited Findings
- `Weather.getCurrentConditions()` "returns the most recently cached weather conditions" as `Weather.CurrentConditions` object or `null`; no fetch-on-demand call in module — [Toybox.Weather](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html)
- `CurrentConditions` fields confirmed: `temperature` (°C), `feelsLikeTemperature` (°C), `highTemperature`/`lowTemperature` (°C), `condition` (enum), `windSpeed` (m/s), `windBearing` (degrees), `relativeHumidity` (%), `precipitationChance` (%), `pressure` (Pa), `uvIndex` (0–10), `visibility` (m), `cloudCover` (%), `dewPoint` (°C), `observationTime` (UTC `Time.Moment`) — [Toybox.Weather.CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- `observationLocationPosition` and deprecated `observationLocationName` need position permission to be non-null; other fields not permission-gated in class doc — [Toybox.Weather.CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- Min API Level for `getCurrentConditions()`/`getHourlyForecast()`/`getDailyForecast()` 3.2.0; `getSunrise()`/`getSunset()` (explicit location + date params, not current conditions) need API 3.3.0, "more limited device support" — [Toybox.Weather](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html)
- All `CurrentConditions` fields "may return null" — [Toybox.Weather.CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- App-review battery guidance elsewhere on dev portal: "frequent weather updates ... can reduce battery life," implying weather refresh device-managed, not app-managed, cadence and cost — [Connect IQ App Review Guidelines listing, via search snippet](https://developer.garmin.com/connect-iq/app-review-guidelines/) (snippet only; page did not render for direct fetch — see Gaps)

### Inferences
- No app-triggered "refresh now" call -> morning dress-for-weather feature depends on existing Garmin Connect Mobile / device weather-sync schedule (commonly hourly-ish on synced devices, GPS-assisted on some models). App reads last cache only, never forces fresh pull.
- No manifest permission needed for temperature/precip/UV/wind values; `Positioning` only needed for observation location itself (not needed for dress-for-weather logic).

### Gaps
- Exact refresh cadence (e.g., "every 60 minutes," "on phone Bluetooth reconnect only," "GPS-fix triggered") not documented on API reference pages reachable via fetch; Weather module doc states no sync interval. Needs Garmin forum statement from Garmin employee or empirical device logging — not found this pass.
- Could not confirm whether weather sync works without paired phone (e.g., built-in LTE/Wi-Fi models) vs strictly requiring Garmin Connect Mobile relay — `core-topics` pages (Positioning, Backgrounding) likely addressing this returned only navigation-menu content (JS-rendered SPA not captured by fetch tool) -> unverified from primary source this pass.

## Is there a native Connect IQ API for calendar/next-event data, or does it require a companion app / phone-side push? What's the realistic feasible approach for "next event starts/ends" on-device?

### Takeaway
**No native calendar/agenda API** in Connect IQ. Only realistic on-device path: companion (phone-side) app pushing next-event data to watch via `Toybox.Communications` phone-app messaging (foreground and, per forum confirmation, also background-eligible), landing in **widget or device app** — not watch face, since watch faces cannot use Communications at all.

### Cited Findings
- "If you want to get calendar data from a phone, you can't do it from a Connect IQ watchface, as no communication is allowed in a watch face. However, you could do it in a widget or watch-app." — [Garmin Forums: Calendar API discussion](https://forums.garmin.com/developer/connect-iq/f/app-ideas/280141/calendar-api)
- Community request thread frames native calendar API as standing **feature request**, not shipped capability: "it would be great if the agenda items on the device would be readable through a Calendar API" — [Garmin Forums: Calendar API](https://forums.garmin.com/developer/connect-iq/f/app-ideas/280141/calendar-api)
- Connect IQ data fields (in-activity metric type) "can't get data from a phone either" — same thread — [Garmin Forums: Calendar API](https://forums.garmin.com/developer/connect-iq/f/app-ideas/280141/calendar-api)
- `registerForPhoneAppMessages()` / `transmit()` in `Toybox.Communications` let watch app exchange messages with companion phone app; messaging usable "not just in foreground apps but also in background services" per forum discussion of Background module — [Garmin Forums: Background module - companion app communication](https://forums.garmin.com/developer/connect-iq/f/discussion/6168/background-module---is-companion-app-communication-supported-in-the-background); class reference: [Toybox.Communications.PhoneAppMessage](https://developer.garmin.com/connect-iq/api-docs/Toybox/Communications/PhoneAppMessage.html)
- Garmin's own "Glance" showcase app is exactly this pattern: widget paired with Android companion app pushing dashboard data to watch — [Garmin Forums: Glance showcase](https://forums.garmin.com/developer/connect-iq/f/showcase/6160/glance---phone-dashboard-widget-with-android-companion-app/40784)
- Background services can also be driven by scheduled **temporal events** (time-based, not just phone-push), but temporal event alone cannot manufacture calendar data — only polls/reads what companion already deposited in app storage; throttled to no more than one temporal event per 5 minutes per app (see Background section below) — [Garmin Forums: Background => Temporal Event](https://forums.garmin.com/developer/connect-iq/f/discussion/5443/background-temporal-event)

### Inferences
- Realistic architecture for "next event starts/ends": **widget (or device app), not watch face**, receiving push messages from phone-side companion app (reads OS calendar), storing next-event payload in `Application.Storage`/property storage, temporal-event-driven background service (5-minute floor) refreshing on-screen countdown/label between pushes.
- Watch faces barred from Communications -> "next event" glance cannot live directly on always-visible watch face complication slot unless read from Garmin's own Complications system fed by value widget/companion already wrote to shared storage. Complications' data-source model for third-party custom values not confirmed feasible this pass (see Gaps; Complications question out of scope of listed key questions but adjacent).

### Gaps
- Whether widget can republish pushed data into native Complication slot (so it *appears* on watch face itself) not confirmed. `Toybox.Complications` core-topics page and API pages describe complications as read access to Garmin's own built-in metrics (steps, HR, Body Battery, etc. — see `Complications.getComplication(id)`, `Complications.Iterator`) with subscribe/callback model; no primary-source text retrieved confirming or denying whether third-party app can register as **complication data provider** with custom data (e.g., "next event"). Needs direct read of `developer.garmin.com/connect-iq/core-topics/complications/`, which did not render through fetch tool this pass (JS-rendered page, only nav returned).
- No data on typical push latency/reliability of phone→watch Communications messaging for this use case.

## What does Toybox.ActivityMonitor / Toybox.SensorHistory expose for stress score and Body Battery — refresh rate, and which device generations/API levels support each?

### Takeaway
Stress score exposed as live snapshot via `ActivityMonitor.Info.stressScore` (API 5.0.0+, narrow device list) and as history via `SensorHistory.getStressHistory()` (API 3.3.0+, broader device list). Body Battery **history-only** — no live Body Battery field in `ActivityMonitor.Info`, only `SensorHistory.getBodyBatteryHistory()` (API 3.3.0+). Neither API documents fixed sample interval; both stated device-dependent.

### Cited Findings
- `ActivityMonitor.Info.stressScore`: `Number` or `null`, 0–100 scale (0–25 Resting, 26–50 Low, 51–75 Medium, 76–100 High), "calculated using a rolling average of the last 30 seconds of stress level readings," min API level 5.0.0, device support limited to newer models such as fēnix 7 series+, Forerunner 165+, Venu 2+ — [Toybox.ActivityMonitor.Info](https://developer.garmin.com/connect-iq/api-docs/Toybox/ActivityMonitor/Info.html)
- **Body Battery not present as field in `ActivityMonitor.Info`** — confirmed absent from class's documented fields — [Toybox.ActivityMonitor.Info](https://developer.garmin.com/connect-iq/api-docs/Toybox/ActivityMonitor/Info.html)
- `SensorHistory.getBodyBatteryHistory()` returns `SensorHistoryIterator` of 0–100 samples ("0 indicates the body is drained ... 100 indicates the body is rested and charged"); min API level 3.3.0; "the time between each SensorSample in the iterator may be device dependent" (no fixed interval documented); "this function always returns the most recent sensor history samples" (no stated poll/refresh frequency); supported on ~90+ devices including fēnix 6+, Forerunner 245+, Venu series, Instinct series — [Toybox.SensorHistory](https://developer.garmin.com/connect-iq/api-docs/Toybox/SensorHistory.html)
- `SensorHistory.getStressHistory()` returns 0–100 samples (higher = more stress); min API level 3.3.0; device-dependent sample interval, ~80+ devices supported, excluding some older fēnix/Forerunner models that support Body Battery — [Toybox.SensorHistory](https://developer.garmin.com/connect-iq/api-docs/Toybox/SensorHistory.html)
- Known SDK bug reported: "oldest and newest sample time of the body battery and stress iterator are not properly initialized" — relevant if spec relies on precise sample timestamps — [Garmin Forums bug report](https://forums.garmin.com/developer/connect-iq/i/bug-reports/oldest-and-newest-sample-time-of-the-body-battery-and-stress-iterator-are-not-properly-initialized)
- Community/DC Rainmaker coverage corroborates stress, Body Battery, remaining recovery time access added to Connect IQ API in platform updates — [DC Rainmaker: Garmin's Connect IQ Platform Updates](https://www.dcrainmaker.com/2021/10/garmins-connect-platform.html)

### Inferences
- Evening Body Battery summary must be built from `SensorHistory.getBodyBatteryHistory()` (history/graph-style iterator), not single live "current Body Battery" field — none in public API.
- Midday stress-based "reset nudge" should design for two-tier device reality: `ActivityMonitor.Info.stressScore` (live number, API 5.0.0, newest devices only) = higher-quality signal where available; `SensorHistory.getStressHistory()` (API 3.3.0, wider support) = fallback for older-but-still-common devices (matters directly for target device, Forerunner 965, which needs checking against both device-support lists).
- `timeToRecovery` (hours, API 3.3.0, broad device support back to fēnix 5 Plus) = documented, easy-to-reach adjacent field that could support evening summary alongside Body Battery.

### Gaps
- No documented numeric sample interval (e.g., "every 15 minutes," "every 2 minutes") for stress or Body Battery sensor history found in API reference; Garmin states device-dependent, undocumented at value level. Confirming real-world interval for Forerunner 965 needs forum statement or empirical on-device logging — not obtained this pass.
- Did not confirm exact min API level / firmware version on Forerunner 965 to know whether `stressScore` (5.0.0) or history-only fallback applies; device-lookup task against Garmin's Compatible Devices matrix, not completed here.

## Background Service / temporal-event update budget per device tier, and battery effect of switching content mode several times a day (esp. AMOLED always-on)?

### Takeaway
Connect IQ enforces one hard, documented, cross-device-tier rule: **a given app can run no more than one temporal (time-driven) background event per 5 minutes**, confirmed by Garmin staff reply on developer forum, with no stated exception for AMOLED vs. MIP or for user interaction. No AMOLED-specific *background service* budget (separate from general 5-minute floor) or quantified battery-cost-per-mode-switch figure found in official documentation this pass.

### Cited Findings
- "Applications can never run more than one Temporal event of any type within 5 minutes of the last one that ran for that application, no exceptions." "The user's interaction with your widget does not change this restriction." Garmin representative, replying in same thread, confirmed: "The design does limit this use case, and there are not any plans to change the limitation at this time." — [Garmin Forums: Background => Temporal Event](https://forums.garmin.com/developer/connect-iq/f/discussion/5443/background-temporal-event)
- Background events can also be triggered by non-temporal system events (e.g., activity goal met) besides scheduled temporal events — [Toybox.Background module description, via search snippet](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html) (page did not render through fetch — see Gaps)
- General battery guidance from dev portal (found via search snippet, not confirmed by direct fetch): "complex watch faces, frequent weather updates, always-on seconds, maps, and background connections can reduce battery life" — attributed to Garmin's own developer site content but **not independently verified by direct page fetch this pass**; treat as directionally credible but unconfirmed wording.

### Inferences
- Time-of-day adaptive design changing watch-face/widget content mode "several times a day" (morning → midday → evening) well within 5-minute floor (transitions hours apart, not sub-5-minute) -> temporal-event budget not binding constraint for this feature's cadence.
- 5-minute floor means design cannot rely on background service for fine-grained "next event in N minutes" countdown ticking; on-screen tick for something like break/walk nudge must be computed from stored target timestamp and rendered by normal `onUpdate()`/`onPartialUpdate()` draw cycle (runs on device's own display-refresh schedule), not driven by repeated background wakes.
- No official, quantified "battery cost of N content-mode switches per day" figure located; only empirical device testing (per project's own house rule that "simulator passing is not device proof") can produce real number for Forerunner 965.

### Gaps
- Could not confirm whether 5-minute floor differs between full-color low-power ("always-on/AOD") AMOLED behavior and non-AMOLED MIP behavior — forum thread and module docs describe limit as universal, but no source explicitly states "and this is identical across AMOLED and MIP tiers" vs simply never addressing the distinction.
- Could not retrieve full text of `developer.garmin.com/connect-iq/core-topics/backgrounding/` or "How Do I Create a Connect IQ Background Service" FAQ page — both returned only site navigation (JS-rendered pages not captured by fetch tool), so any additional device-tier nuance (canonical source for topic) unverified this pass. Follow-up with JS-capable fetch or manual browse of those two URLs recommended before finalizing spec.
- No official quantified battery-drain number for AMOLED always-on mode generally, or repeated draw-mode switching specifically, found from Garmin. Any figure in circulation = third-party estimate, not vendor-documented.

## Verify the "no pixel fully lit for more than ~4 minutes continuous" AMOLED burn-in guidance — documented Garmin constraint, community rule of thumb, or unverifiable?

### Takeaway
**Community rule of thumb, not documented Garmin developer-portal constraint** — and commonly repeated figure in Connect IQ developer forum discussions is **3 minutes**, not 4. No official Garmin developer documentation page found (this pass) stating any specific numeric time limit; two numbers recurring in forum discussion are "no more than 10% of pixels on at once" and "no single pixel on for more than ~3 minutes," both sourced to developer-forum threads, not citable Garmin spec page.

### Cited Findings
- Garmin Forums thread on AMOLED always-on/sleep-mode rules: "The rules of no more than 10% of pixels on and no pixel on for more than 1 minute apply to AMOLED watches" for older devices; forum participant separately states "the max of a single pixel being on for more than 3 minutes is what changed for the Venu 2," and notes rule "may not be used for some devices" — forum participants themselves disagree on exact figure and device scope — [Garmin Forums: Always on display (sleep mode) behaviour and rules on newer AMOLED watches](https://forums.garmin.com/developer/connect-iq/f/discussion/322419/always-on-display-sleep-mode-behaviour-and-rules-on-newer-amoled-watches)
- Same thread: "if you have any graphic element 2 pixels or more wide or tall ... then a 1 pixel shift in 2 directions is not enough to avoid breaking the 3 minute rule" — again forum tribal knowledge, not quoted spec — [Garmin Forums: 322419](https://forums.garmin.com/developer/connect-iq/f/discussion/322419/always-on-display-sleep-mode-behaviour-and-rules-on-newer-amoled-watches)

### Inferences
- "~4 minutes" figure product-spec side has carried appears imprecise recollection of "~3 minute" figure circulating in Connect IQ developer forums. Treat underlying constraint as real (AMOLED devices enforce some forced-dim/blackout behavior in always-on mode to protect panel) but specific number **unverified and likely off by one**; do not cite "4 minutes" as Garmin fact in product spec.

## Connect IQ permission requirements or store-review implications tied to background service / sensor access / weather?

### Takeaway
Weather field access (temperature, precip, UV, wind) needs **no manifest permission**; only location fields on `CurrentConditions` require `Positioning`. Background services and sensor/`SensorHistory` access governed by general manifest permission system and Garmin's App Review Guidelines, but actual guideline text (battery-impact review criteria, background-service review checklist) could not be retrieved as body text this pass — review-guidelines and manifest-and-permissions pages both rendered as navigation shells only.

### Cited Findings
- `Positioning` permission required specifically for `Weather.CurrentConditions.observationLocationPosition` / `observationLocationName`; other weather value fields (temp, precip, UV, wind, humidity, etc.) not gated by stated permission in class doc — [Toybox.Weather.CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- Garmin publishes dedicated "Manifest File and Permissions" core-topics page and separate "App Review Guidelines" page, both canonical sources for this question, but both returned only site-navigation content when fetched this pass (no article body captured) — [Manifest and Permissions](https://developer.garmin.com/connect-iq/core-topics/manifest-and-permissions/); [App Review Guidelines](https://developer.garmin.com/connect-iq/app-review-guidelines/)
- Garmin Customer Support maintains consumer-facing FAQ titled "Permissions for Connect IQ Applications," confirming permissions are user-visible/consent-relevant concept at install time, not just manifest formality — [Garmin Support: Permissions for Connect IQ Applications](https://support.garmin.com/en-US/?faq=Z8zVsJfH3v1KAhrFTNmZi8)
- Communications (phone-app messaging, used for calendar/next-event approach) subject to own permission problems reported by developers, per forum discussion title "Permissions problem using Toybox.Communications," indicating live pain point worth testing early, not assuming — [Garmin Forums: Permissions problem using Toybox.Communications](https://forums.garmin.com/developer/connect-iq/f/discussion/260809/permissions-problem-using-toybox-communications)
- General battery-impact guidance surfaced via search snippet (not independently confirmed by direct fetch): background connections and frequent weather updates called out as things that "can reduce battery life," suggesting Garmin's review process sensitive to background/weather usage patterns during submission review, but exact review checklist criteria unconfirmed — [App Review Guidelines, via search snippet only]

### Inferences
- For product spec: budget explicit manifest permission review for `Positioning` (only if location-name/observation-location used — likely skippable if app just reads temp/precip/UV/wind) and for `Communications` (needed for companion-app next-event push design), plus whatever sensor permission gates `ActivityMonitor`/`SensorHistory` (typically permission-free for on-device stress/Body Battery reads since first-party health data already on watch, but spot-check against manifest doc directly, not assume).
- Given forum-reported friction with Communications permissions, calendar/next-event feature (depends on Communications) carries more store-review and runtime-permission risk than weather or Body Battery features; give device-testing priority.

### Gaps
- Full text of Garmin's official Manifest and Permissions page and App Review Guidelines page not retrieved — both JS-rendered pages fetch tool could not extract past navigation shell. Single most important follow-up before finalizing spec: someone opens both pages directly (browser) and extracts (a) full permission list with per-API mapping, (b) any explicit review criteria mentioning background services, sensor polling frequency, or battery-impact thresholds.
- No confirmation whether `ActivityMonitor.Info.stressScore` / `SensorHistory` body-battery/stress access requires any manifest permission at all (plausibly permission-free as first-party on-device data, but not confirmed from permissions-specific primary source this pass).
