Research date 2026-09-26. Local SDK = Connect IQ SDK 9.2.0 (`connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2`), docs generated 2026-06-09. Source tags: "SDK doc" = HTML shipped in the local SDK `doc/` folder; "Device data" = `~/Library/Application Support/Garmin/ConnectIQ/Devices/<id>/compiler.json` and `simulator.json` (installed with the SDK, simulator/compiler config, not marketing docs); "Experiment" = a throwaway probe project I compiled with the local `monkeyc` 9.2.0 (scratch dir, nothing written to the repo; probe described below so it can be re-created); "Forum" = forums.garmin.com Connect IQ developer forum (community and Garmin staff posts, weight accordingly, speaker named where I could see one). Per-device tables (glance memory, live updates, content area for all 80 products) are in the sibling note `device_support_and_memory.md`; this note only quotes what is needed.

Probe project used for every "Experiment" bullet: `type="watch-app"`, `minApiLevel="3.4.0"`, all 80 HeroSet product ids; `class ProbeApp extends AppBase` with `initialize()` constructing an unannotated `ProbeStore`, `onStart` printing `state.get(:launchedFromGlance)`, `getInitialView()` returning an unannotated `ProbeView`, and `(:glance) function getGlanceView() as [GlanceView] or [GlanceView, GlanceViewDelegate] or Null { return [ new ProbeGlance() ]; }`; `(:glance) class ProbeGlance extends WatchUi.GlanceView` drawing with `Graphics.FONT_GLANCE`; a `<string id="G" scope="glance">` resource. Probe source (approximately what was compiled; `ProbeStore`/`ProbeView` are deliberately not annotated):

```monkeyc
import Toybox.Application; import Toybox.Lang; import Toybox.WatchUi; import Toybox.System; import Toybox.Graphics;
import Toybox.ActivityMonitor; import Toybox.Time; import Toybox.Time.Gregorian; import Toybox.Application.Storage;
class ProbeStore { var v as Number = 3; function initialize() {} }
class ProbeApp extends Application.AppBase {
    private var _store as ProbeStore;
    function initialize() { AppBase.initialize(); _store = new ProbeStore(); }
    function onStart(state as Dictionary?) as Void { System.println("onStart glance=" + (state != null ? state.get(:launchedFromGlance) : "nil")); }
    function getInitialView() as [Views] or [Views, InputDelegates] { return [ new ProbeView() ]; }
    (:glance)
    function getGlanceView() as [GlanceView] or [GlanceView, GlanceViewDelegate] or Null { return [ new ProbeGlance() ]; }
}
class ProbeView extends WatchUi.View {
    function initialize() { View.initialize(); }
    function onUpdate(dc as Dc) as Void { dc.clear(); dc.drawText(10, 10, Graphics.FONT_SMALL, WatchUi.loadResource(Rez.Strings.FullOnly) as String, Graphics.TEXT_JUSTIFY_LEFT); }
}
(:glance)
class ProbeGlance extends WatchUi.GlanceView {
    function initialize() { GlanceView.initialize(); }
    function onUpdate(dc as Dc) as Void {
        dc.drawText(0, 0, Graphics.FONT_GLANCE, "hi " + dc.getWidth() + "x" + dc.getHeight(), Graphics.TEXT_JUSTIFY_LEFT);
        var s = Storage.getValue("k"); var app = Application.getApp() as ProbeApp; var n = ActivityMonitor.getInfo().steps;
        var t = Gregorian.info(Time.now(), Time.FORMAT_SHORT); var p = Application.Properties.getValue("Foo");
        var a = WatchUi.loadResource(Rez.Strings.G) as String;        // scope="glance" string: OK
        var b = WatchUi.loadResource(Rez.Strings.FullOnly) as String; // foreground string: flagged at -l 2/3
        var st = new ProbeStore(); helper();                           // unannotated: flagged at -l 2/3
    }
}
function helper() as Void {}
```

The all-80-products build (`monkeyc -f monkey.jungle -o all.iq -e -w`, no `-l`) ended `BUILD SUCCESSFUL` with no ERROR lines; 86 "Glance applications are not supported" warnings, all on the 17 CIQ 3.4 products (several warnings per product because two annotated locations and resources each warn).

## 1. Exact API, annotations, return type, what the callbacks can do, API levels

### Takeaway
A glance is `AppBase.getGlanceView()` returning `[GlanceView]` or `[GlanceView, GlanceViewDelegate]` or `null`, with the glance code marked `(:glance)`; the API is CIQ 3.1.0 (not 3.3), but for a `watch-app` it only takes effect on devices at CIQ 4.0+ (SDK 4.0.0 added watch-app glances). The glance view is a normal `WatchUi.View` on a small clipped `Dc`: `onLayout`/`onShow`/`onUpdate`/`onHide` run, layers and page stacks do not, `onPartialUpdate` does not exist for it, and the delegate is a no-op.

## 2. Manifest, permissions, launcher icon, Storage/Properties, Toybox modules available in glance scope

### Takeaway
No manifest change: the glance uses the app's existing `launcherIcon`, needs no permission of its own and no new resource, only the `(:glance)` scoping of code and (for anything not already `background`-scoped) `scope="glance"` on resources. `Application.Storage`, `Properties`, `Time`/`Gregorian`, `ActivityMonitor`, `getApp()`, `WatchUi.loadResource` (glance-scoped resources only), fonts and bitmaps all work; each Toybox module you use still needs its manifest permission (e.g. `Sensor`).

### Cited Findings
- Glances topic: "Most functionality supported in Widget is still supported when running as a Glance, such as accessing application storage and making web requests. However, developers should focus on making WatchUi.GlanceView quick to load and moving CPU intensive work to a Background service." — [SDK doc Glances.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Glances.html)
- No glance-specific manifest attribute, permission or resource type is documented; the Manifest and Permissions topic has no glance content (grep of the SDK doc: only the nav-bar "Glances" link). The glance icon is not a separate resource: the simulator device data draws an `iconArea` next to the glance content area (fr965: icon 65x65 at (59,43), content 299x148 at (132,2)), and the forum states the default (no-override) glance on CIQ 3 is "the launcher icon and app name"; I inferred the system uses the manifest `launcherIcon` for the icon and did not find that spelled out for CIQ 4+ apps. — [SDK doc Manifest_and_Permissions.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Manifest_and_Permissions.html); [Device data fr965 simulator.json `glance`](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Devices/fr965/simulator.json)

- `Application.Storage` Since 2.4.0 (limits per Persisting Data: keys and values 8 KB each, 128 KB total; a forum poster quotes "values are limited to 32 KB" from documentation, conflicting, see [Forum thread](https://forums.garmin.com/developer/connect-iq/f/discussion/412304/memory-requirements-when-storing-json-from-glance/1936392)); no glance restriction is documented, and the `Storage` module page has no runtime-context restriction. `Application.Properties` likewise. `AppBase.getProperty` throws `ObjectStoreAccessException` only "if called from a background process". — [SDK doc Persisting_Data.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Persisting_Data.html); [SDK doc Application.Storage](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/Toybox/Application/Storage.html); [SDK doc Application.Properties](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/Toybox/Application/Properties.html)
- Experiment: inside `(:glance) class ProbeGlance.onUpdate` these compiled with no warning and no error at type-check level 0, 1, 2 and 3: `Storage.getValue("k")`, `Application.getApp() as ProbeApp`, `ActivityMonitor.getInfo().steps`, `Gregorian.info(Time.now(), Time.FORMAT_SHORT)`, `Application.Properties.getValue("Foo")`, `WatchUi.loadResource(Rez.Strings.G)` (string with `scope="glance"`), `Graphics.FONT_GLANCE`, `dc.getWidth()/getHeight()`. ### Inferences
- HeroSet's dashboard reads via `getApp().getStore()`; that works in a glance only if the store class and every class it touches is `(:glance)`-annotated (or the app is restructured), see sections 3 and 4. HeroSet's `resources/` contains only the launcher icon and strings; strings the glance needs must be `scope="glance"`.
- "Only `data/` touches Storage" (HeroSet rule) is compatible: a glance-scoped read path in `data/` is enough; no permission change.

### Gaps
- No Garmin statement enumerating forbidden Toybox calls in glance scope beyond the per-module context lists; I did not test `Sensor` listeners, `Position`, `Communications.makeWebRequest` in a glance, and the `Timer` behaviour differs by device (section 4).
- The meaning of the SDK doc's "App Types and Runtime Contexts" list is my interpretation.

## 3. Memory: limits, `(:glance)` scoping, how counted, failure modes, how to measure

### Takeaway
Glance heap limit is 64 KB on the 63 CIQ 5.0+ HeroSet products and 32 KB on the 17 CIQ 3.4 products (which get no watch-app glance anyway); the Core Topics text "32KB for most devices" is stale. `(:glance)` decides which functions/classes/resources are compiled into the glance process; the `AppBase`-derived class is always loaded whole, including `initialize()`, `onStart()` and every method body, so a HeroSet-style app class that builds a store and sync coordinator in `initialize()` is the main hazard.

### Cited Findings
- Glances topic: "it will be started in Glance mode with limited memory allocated (32KB for most devices)". Similar to background services, `(:glance)` "indicate[s] which modules and / or classes are necessary when running a Widget in Glance mode ... selectively allows developers to limit memory usage". — [SDK doc Glances.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Glances.html)
- Device data (current per-device numbers): `appTypes[type=glance].memoryLimit` = 65536 bytes on all 63 HeroSet products at API 5.0/5.1/5.2/6.0 (e.g. fr965: glance 65536, watchApp 786432, background 65536); 32768 on the 17 API 3.4 products (e.g. fenix6, marq*, descentmk2, fr945lte, enduro). Counts computed from `compiler.json` for the 80 manifest ids. Conflicts with the Glances doc's "32KB for most devices" (doc predates the newer, larger devices). — [Device data fr965 compiler.json](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Devices/fr965/compiler.json); per-device table in sibling `device_support_and_memory.md`
- Annotations page: ":glance Denotes code blocks available to when running in Glance Mode."; ":background Denotes code blocks available to the Background process." Background doc analog: "Only modules, classes, functions and member variables decorated with the :background annotation will be compiled into your background service. This means you must decorate all related code with the annotation (including your Application class)." — [SDK doc Monkey_C/Annotations.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Monkey_C/Annotations.html); [SDK doc Backgrounding.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Backgrounding.html)
- Experiment, `monkeyc --build-stats 0` (prints "Data" and "Code" bytes per scope, "Foreground" versus "Glance"), fr965, watch-app: baseline Code Glance 442 B / Foreground 549 B, Data Glance 414 / Foreground 652. Adding a 60-method unannotated class: Foreground code 549 -> 1525, Glance code stays 442 (data +9 B). Adding the same class with `(:glance)`: Glance code 442 -> 1418. Adding 60 statements to the body of the unannotated `AppBase.onStart`: Glance code 442 -> 1359 (Foreground 549 -> 1466). Conclusion: unannotated classes/functions are excluded from the glance image; the `AppBase` subclass and all its method bodies are always in it. — Experiment (monkeyc 9.2.0). The `--build-stats` flag is listed in `monkeyc --help`.
- Type-check levels: `monkeyc -l 0|1|2|3` = "off, gradual, informative, strict". Scope checking ("Value 'X' not available in all function scopes") appeared only at `-l 2` (warning) and `-l 3` (error); with no `-l` (the build command in HeroSet CLAUDE.md passes none) or `-l 1` a glance referencing unannotated code compiles cleanly (whether it then fails at runtime was not run, see Gaps). The same messages fired for an unannotated `AppBase.initialize()` constructing an unannotated class and for `getInitialView()` constructing an unannotated view, i.e. the checker treats `AppBase` methods as glance-visible code. The Monkey Types doc: the checker validates "any member fetched from a module or class is available in all of the same application scopes as the caller" and can be silenced with `:typecheck(disableGlanceCheck)`. — Experiment (monkeyc 9.2.0); [SDK doc Monkey_Types.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Monkey_C/Monkey_Types.html)
- Forum on the same rule: "AppBase is always loaded, as is code with the background annotation. If something is annotated with glance, that will get loaded in glance or full view." (jim_m_58). ### Inferences
- For HeroSet the concrete risk list: `HeroSetApp.initialize()` (`new HeroSetStore(null,null)`, `new HeroSetSyncCoordinator(_store)`), `onStart()` (`_store.ensureCurrentDay()`, `HeroSetComplicationPublisher.publish`), `onStop()` (`_sync.stop()`), `getInitialView()` and the `getStore()`/`getSync()` return types all live in the always-loaded class, and none of those types is `(:glance)` today. If the store/sync classes are not annotated, glance mode would try to construct classes that are not in the glance image (probable runtime crash; I could not run the glance mode in the simulator headless to prove the exact error). The fix space: annotate what the glance needs and guard/lazily create the rest (for example make `_store`/`_sync` lazy accessors, or gate `initialize()`/`onStart()` work on `:launchedFromGlance`, which is only in `onStart` options), and compile with `-l 3` (or at least `-l 2`) so scope violations show up at build time; note `AppBase.initialize()` has no options argument, so glance vs full cannot be known there.
- Budget: 64 KB heap minus the always-loaded app class, the glance view class, fonts/bitmaps and the read path; `--build-stats` gives a static floor, the simulator's Peak Memory gives the dynamic figure. Large Storage reads (dictionary deserialisation) are the likely spike.

### Gaps
- Real per-device peak memory numbers for a HeroSet glance: not measurable without building the glance and running the simulator's memory view.
- Exact runtime error when a non-`(:glance)` class is constructed in glance mode: not verified in the simulator (GUI needed); compile-time behaviour is verified.
- Menu path for the simulator memory view: a search-result summary said "File -> View Memory" and "Peak Memory" is "the best indication of how close to the memory limit you are", but I could not tie that to a page I read; treat the path as unverified. The SDK Debugging/Profiling topics contain no memory-view text.
- Whether the VS Code extension used for HeroSet builds sets a default type-check level: not checked.

## 4. Lifecycle: creation and refresh, onStart, getApp(), live data, timers

### Takeaway
On the 63 eligible products the glance runs live (`liveUpdates` true in device data): the system keeps the glance process alive while scrolling; `requestUpdate()` works and updates should stay under 1 Hz. On non-live devices the app is started, drawn, cached and stopped, at most every ~30 s per visibility. On non-live devices the doc explicitly lists `onStart()`, `getGlanceView()`, the four view callbacks and `onStop()`; for live devices the doc only says the app is started and kept alive (that `onStart()` also runs there is my inference). `getApp()` works in glance code (compiled; runtime not run) and data written by the full app is visible on the next glance draw because it lives in Storage.

### Cited Findings
- Glances topic, "Live UI Update": devices with "ample resources" start the widget in glance mode and keep it alive; the GlanceView "will be updated as needed by the system, and calls to WatchUi.requestUpdate() will trigger a WatchUi.View update as expected"; "It's highly recommended that the update rate should be kept under 1HZ". "Background UI Update": devices "that have less memory" start the app only "when the system deems it appropriate, and calls to WatchUi.requestUpdate() will have no effect. Such a device could update their glance view when it becomes visible (activated) and at least 30 seconds since last update." Footnotes: ample = "Music-capable wearables", less = "Non-music wearables". — [SDK doc Glances.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Glances.html)
- Same page, background-update sequence: "The Application.AppBase functions AppBase.onStart(), AppBase.getGlanceView() will be called to start the app and retrieve the view. Once the WatchUi.GlanceView has been retrieved, the View functions View.onLayout(), View.onShow(), View.onUpdate() and View.onHide() will be called. The AppBase.onStop() function will be called upon app termination". "All content that is rendered to the Graphics.Dc ... will be cached on the filesystem and used to display until the next time the system decides to do an update." "There is no guarantee that a widget will always start in glance mode, for example, before transitioning to its standard widget mode."
- The music/non-music footnote does not match device data. `simulator.json` `glance.liveUpdates` is false for 11 of HeroSet's 80 products (fenix6, fenix6s, enduro, marqadventurer/athlete/aviator/captain/commander/driver/expedition/golfer, all CIQ 3.4 and so not glance-eligible as watch-apps) and true for all 63 API 5.0+ products, including the non-music fr255/fr255s/fr165. - `getApp()`: "After your application is loaded, your application object will be instantiated. From that point forward it will be available throughout the application by calling Application.getApp(). After your application object is instantiated, the AppBase.onStart() function will be called." (general launch text; in the experiment `Application.getApp() as ProbeApp` compiled inside the glance class). — [SDK doc Application_and_System_Modules.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Application_and_System_Modules.html)
- `onStart` in glance mode and the `:launchedFromGlance` option: the Glances topic says `onStart` runs; the `onStart(state)` options doc lists ":launchedFromGlance ... - Glance-list capacity: v3.1.9 "devices that support live glance updates ... can not support more than 4 widgets in the glance mode" fixed. — SDK doc History.html
- User can disable glances (fēnix 6 era; summarized from the announcement thread: Settings > Widgets > Widget Glances on/off); `DeviceSettings.isGlanceModeEnabled` reports it (3.1.4; "will return true for 4.x devices" per v4.1.4 note). — [Forum announcement](https://forums.garmin.com/developer/connect-iq/b/news-announcements/posts/widget-glances---a-new-way-to-present-your-data); SDK doc History.html

### Inferences
- A HeroSet glance that reads today's totals from Storage in `onUpdate()` needs no timer: totals change only while the user is inside the app, the next scroll into the glance list redraws (live) or refreshes (>= 30 s rule, non-live). A per-second `Timer` would be needless memory/CPU.
- Any code in `HeroSetApp.onStart` (day rollover `ensureCurrentDay`, complication publish) also runs on every glance start on non-live devices and at glance-process start on live ones; not harmful but it is glance-scope code that consumes the 64 KB budget and, if it writes (`ensureCurrentDay`), writes from the glance process. Whether a write from a glance process is permitted was not verified.

### Gaps
- Exact system refresh triggers on live devices (scroll into view versus periodic), and whether the glance process is torn down when the list is left: not documented beyond "updated as needed by the system".
- Behaviour in low-power/always-on display: not documented.
- Whether `Storage.setValue` from a glance is allowed/persisted: not documented, not tested.

## 5. Select/tap behaviour, input, getInitialView interplay

### Takeaway
Glance views take no input. The user launches the app by selecting the glance in the list (START/select key or a tap on touch products); the system starts the full app fresh (`onStart` with `:launchedFromGlance`, then `getInitialView()`), and that base view gets full input (no widget restrictions). Apps launched this way are subject to an inactivity timeout that returns the user to the home screen, which is absent when launched from the activity list.

### Cited Findings
- App Types: "Glance views run in a limited runtime space, with reduced memory and privileges and do not accept any input." and, for widgets, "When launched in this context, the widget base view don't have the input restrictions regularly applied." — [SDK doc Connect_IQ_Basics/App_Types.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Connect_IQ_Basics/App_Types.html); [SDK doc Entry_Points.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/User_Experience_Guidelines/Entry_Points.html) ("When launching from a glance, the base page of your widget/app will not have the input restrictions when launching as a widget.")
- Glance list: "Selecting an item from the list launches into the experience. The user can exit by backing out of the base page, but after a period of inactivity, the system will terminate the launched app, as well." — SDK doc Entry_Points.html
- Timeout: "If an app is launched from the glance list, a timeout will be applied to the app. If the user does not exit the app within a given time frame, the system will terminate the app and return to the home screen. If an app is launched from the activity menu, however, it will not time out" (the doc code sample detects `state.get(:launchedFromGlance)` in `onStart`). — [SDK doc Application_and_System_Modules.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Application_and_System_Modules.html)
- Forum (thread "Glances and Widgets: User Input?"): flowstate says pressing START or tapping at a glance pushes the initial view, "All apps which appear [in] the widget/glance loop ... can accept full user input (buttons and touch), once the user 'opens' the app by pressing START"; jim_m_58 says apps from the glance loop "will time out after a certain period of inactivity" on watches but not on Edge; flowstate says a device app started from the glance loop cannot record an activity (old widget restrictions). — [Forum: Glances and Widgets: User Input?](https://forums.garmin.com/developer/connect-iq/f/discussion/401977/glances-and-widgets-user-input)
- `DeviceSettings.isGlanceModeEnabled` "If glance mode is enabled, the system will pass up / down key events to a widget base page. Otherwise, the system will mask them out." (a widget-era flag; App Types: if defined and true "you can launch directly into the interactive portion of your widget", else the base view). — [SDK doc DeviceSettings](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/Toybox/System/DeviceSettings.html); App_Types.html
- Release notes: v4.0.0 `:launchedFromGlance` added; v6.2.0 "Launch an app in normal mode instead of glance when calling exitTo()"; v4.0.6 "Enable System.exit() for widget apps launched from glance mode". — SDK doc History.html
- Related launch option from the Complications topic: hold-to-launch on a complication starts the publisher app with `:launchedFromComplication` (complication id) in `onStart` options, distinct from `:launchedFromGlance`. — [SDK doc Complications.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Complications.html)

### Inferences
- HeroSet is a workout-style app the user may sit in for long periods (sets, rest timers). If it is entered from the glance, the doc'd inactivity timeout may terminate it mid-workout, whereas the activity-list entry does not time out. This is the largest behavioural risk of adding a glance and is worth a device test on the FR965 (simulator does not show it, per forum). Whether "inactivity" resets on button presses or rep detection is not documented.
- `getInitialView()` needs no change: both entry paths call it. The only branch worth having is `state.get(:launchedFromGlance)` in `onStart` if the timeout needs to be mitigated or logged. The dev build's Fit/Connect Sync code, if any, would run under the "cannot record an activity" restriction when launched from the glance (per forum only; not verified).

### Gaps
- Whether a user has to add HeroSet to the glance list manually on CIQ 4+ devices (discoverability, glance ordering/folders): not verified.
- Timeout length and reset rules (no doc gives a duration; a search-result summary mentioned "a minute or two" on watches, not tied to a page I read, so unverified); whether the "no recording from glance" rule applies to watch-apps on API 5.x/6.x; back-button behaviour from the base page (docs: user backs out of the base page and exits, list behaviour after exit not described).
- `GlanceViewDelegate.onGlanceEvent` events: doc says "none for now".

## 6. Watch-app glance vs widget; separate widget and Storage; Complications subscription

### Takeaway
On CIQ 4.0+ "widget" builds are output as watch-apps anyway, so a watch-app glance and a widget glance are the same mechanism; the difference is entry point (activity/app list versus glance-only widgets on old devices) and that watch-apps can record activities when launched from the activity list. A separate widget app cannot read HeroSet's Storage (each app has its own object store; there is no cross-app API) and, per the docs, Complications can be subscribed to only by watch faces, which matches ADR-044.

### Cited Findings
- Widgets before CIQ 4: carousel from the watch face; CIQ 4.0+: "widgets are now from the app launcher, and apps can have glances"; "Widgets still build and run for API level 4.0 products without modification." — [SDK doc Application_and_System_Modules.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Application_and_System_Modules.html); forum bug report: "When building an app with 'widget' in the manifest, the output type is actually 'watch-app' (device app)" on CIQ 4 devices — [Forum bug report](https://forums.garmin.com/developer/connect-iq/i/bug-reports/when-app-type-is-widget-in-manifest-xml-and-getglanceview-is-not-overridden-compiler-should-automatically-provide-default-glance-view-for-ciq-4-devices-for-max-portability)
- Widget vs app characteristics: "Unlike apps, Widgets time out after a period of inactivity and are not allowed to record activities, but they are also launchable at any time." UX guideline: "Device apps are launchable experiences that do not time out ... On devices with API level 4.0, you can add a glance for device apps." — [SDK doc App_Types.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Connect_IQ_Basics/App_Types.html); [SDK doc Developing_the_Concepts.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/User_Experience_Guidelines/Developing_the_Concepts.html)

- Storage isolation: `Application.Storage` API takes a key only (no app id, no scope parameter), "The Storage module provides persistent storage to applications", "a total of 128 KB of storage is available"; the SDK docs I read do not state in words that one app cannot read another's Storage. The only documented cross-app data channel I found is Complications (publish/subscribe, watch faces subscribe). — [SDK doc Persisting_Data.html](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Persisting_Data.html); [SDK doc Toybox.Application.Storage](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/Toybox/Application/Storage.html)

### Inferences
- A separate widget app (own app id, own object store, no Complications subscription, no glance shared with HeroSet) cannot see HeroSet's daily totals except through a phone/web round trip, so a glance has to live inside HeroSet itself. This agrees with the API shape but the "can't read another app's Storage" claim is inferred from the API, not quoted from a doc.
- The `glancePreview` complication attribute is an unexplored alternative/complement: it needs CIQ 4.2.0+ and a complication resource per product (HeroSet already ships `resources-complications/` for such products), but it applies to "glance folders" (a firmware feature I did not find documented beyond the attribute row).

### Gaps
- No doc statement that another app's Storage is unreadable (inferred).
- What a "glance folder" is on which devices and how `glancePreview` renders; not documented in the SDK pages I read.
- Whether any non-watch-face type can call `Complications.subscribeToUpdates` (docs say no; not tested).

## 7. Glance size, shape, guidelines, safe margins

### Takeaway
The glance `Dc` is a rectangle (the list row's content area, excluding the app icon), not the round screen; its size is per-device and small (about 140-359 px wide, 63-164 px tall across the 80 products, per device data), so lay out from `dc.getWidth()/getHeight()` and `FONT_GLANCE*` at runtime, never hard-coded. Garmin publishes no glance layout or margin guideline that I could find; the only hard data are the per-device rectangles in the SDK device data.

### Inferences
- Because the dc is rectangular and pre-clipped to the content area, HeroSet's existing circle-based "fit against radius + margin" helpers (`HeroSetDraw.fits`, ADR-036) do not apply as-is; the glance layout needs rectangular measure (width x height), and the rule of thumb from device data is two text rows on 63 px rows, three on the taller AMOLED rows (forum), so a glance of "three mission bars + streak" (docs/ideas.md) has to collapse to compact bars (e.g. three thin bars plus one number) on the 103-px and 63-px rows.
- Whether the dc origin and clip equal the `contentArea` rectangle, or whether `getWidth()` returns exactly `contentArea.width`: the docs say the dc is "bounded by glance area"; the forum post that lists 151x63/171x63/191x63 matches `contentArea` for the fēnix 6 family, which supports this, but it is an inference.

### Gaps
- No Garmin-published safe margin for glances; `contentArea` in simulator device data has no stated padding meaning.
- Real hardware glance rectangles versus simulator data: not verified on device.
- The `cacheUpdate` key in `simulator.json` `glance` (false on AMOLED, absent on some MIP) is undocumented; presumably relates to the "cached on the filesystem" behaviour on non-live devices, unverified.

## 8. Testing and monkeyc gotchas

### Takeaway
The simulator supports glances via a device-settings menu item (SDK release notes: "Settings > Glance Launch Mode"), and File > View Memory shows peak memory; Run No Evil unit tests run in the simulator only and have no glance mode, so test glance code by instantiating the `(:glance)` view against a `BufferedBitmap` Dc and by compiling with a strict type-check level. Biggest gotchas: scope errors are silent below `-l 2`, and the `AppBase` subclass is always in the glance image.

### Cited Findings
- Simulator glance support: "Add support for widget glances" (v3.1.3); "Move Glance View option from the Simulation to the Settings menu, and treat it like a device setting" (v3.2.1); "Change Settings > Glance View to Settings > Glance Launch Mode" (v4.1.4); "Update input handling for glance view to re-launch the app in glance view if the glance for the active app is selected" (v3.2.1); v8.2.0 "Fix widget app types not launching in glance mode".
