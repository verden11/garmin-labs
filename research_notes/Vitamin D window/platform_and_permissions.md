# Connect IQ platform capabilities for a "Vitamin D sun window" widget/app (weather, background, inactivity, nudging, permissions, glance, sun position)

Research date 2026-10-04. SDK in use: Connect IQ SDK 9.2.0 (generated 2026-06-09; "System 9, API 9.2.0"). No code was written and nothing was run on a watch.

**How to read the evidence grades (used in every bullet):**

Read from the local SDK 9.2.0 copy (`~/Library/Application Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/`); the public URL given is the same page on developer.garmin.com. ## 1. Weather inputs: UV index, cloud cover, precipitation chance, condition enum — fields, API levels, devices, permission

### Takeaway
`Toybox.Weather` gives UV index (0–10 Float) and cloud cover (0–100 Number) on `CurrentConditions` and `HourlyForecast` only, both introduced at API level 5.1.0 (SDK 8.0.0); precipitation chance and a 54-value condition enum exist since API 3.2.0 on current, hourly and daily objects. No manifest permission is needed to read the values; only the observation-location fields need `Positioning`. UV/cloud therefore reach only watches at API 5.1+ (66 watch products plus 9 Edge/eTrex in SDK 9.2.0; no UV on 3.x–5.0 watches), and every field is nullable, with no real-device evidence found that UV/cloud are actually populated.

### Cited Findings
- `CurrentConditions.uvIndex` is `Lang.Float or Null`, "The UV index [0-10]", Since API Level 5.1.0; `cloudCover` is `Lang.Number or Null`, "[0-100%]", Since API Level 5.1.0. Both also exist on `HourlyForecast` (same types, same 5.1.0). [SDK doc: CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html); [SDK doc: HourlyForecast](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/HourlyForecast.html); live re-fetch of the CurrentConditions page confirms uvIndex and cloudCover at 5.1.0.
- The compiler model agrees: `uvIndex` and `cloudCover` carry `minSdk = "5.1.0"` in `api.mir` on both classes, while `precipitationChance`, `condition`, `temperature` etc. are 3.2.0. [SDK data: api.mir](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/bin/api.mir)
- The SDK release notes place the new fields in v8.0.0: "Add new fields to Weather.CurrentConditions and Weather.HourlyForecast objects"; the simulator gained "support for setting new weather data: UV index, dew point, visibility, pressure and cloud cover". Notifications also arrived in 8.0.0. [SDK doc: Release Notes](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Readme/History.html)
- `DailyForecast` has only `condition`, `forecastTime`, `highTemperature`, `lowTemperature`, `precipitationChance` (no UV, no cloud cover). [SDK doc: DailyForecast](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/DailyForecast.html)
- `HourlyForecast` fields: `cloudCover`, `condition`, `dewPoint`, `forecastTime`, `precipitationChance`, `relativeHumidity`, `temperature`, `uvIndex`, `windBearing`, `windSpeed` (no per-hour feels-like). `CurrentConditions` additionally has `feelsLikeTemperature`, `highTemperature`, `lowTemperature`, `observationTime`, `observationLocationPosition`, `pressure`, `visibility`. [SDK doc: HourlyForecast](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/HourlyForecast.html); [SDK doc: CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- `precipitationChance` is `Lang.Number or Null`, [0-100%], Since 3.2.0 on `CurrentConditions`, `HourlyForecast` and `DailyForecast`. [SDK doc: CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- The condition enum `Weather.CONDITION_*` has 54 values, 0 (`CONDITION_CLEAR`) to 53 (`CONDITION_UNKNOWN`), all Since API 3.2.0 (includes `CONDITION_FOG` 8, `CONDITION_HAZY` 9, `CONDITION_THIN_CLOUDS` 52, `CONDITION_PARTLY_CLOUDY` 1, `CONDITION_MOSTLY_CLOUDY` 2, `CONDITION_CLOUDY` 20, `CONDITION_MOSTLY_CLEAR` 23, `CONDITION_PARTLY_CLEAR` 22, `CONDITION_FAIR` 40, the rain/snow/storm family, `CONDITION_SMOKE` 33, `CONDITION_DUST` 30, `CONDITION_VOLCANIC_ASH` 38). [SDK doc: Toybox.Weather](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html)
- The `Weather` module itself is Since API 3.2.0; `getSunrise` / `getSunset` are Since 3.3.0 and their device list differs from the module's. [SDK doc: Toybox.Weather](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html)
- Per-field device lists are NOT published: the `uvIndex`/`cloudCover` attribute entries carry no "Supported Devices" block, so device support follows the API level. From each device's `compiler.json` (`deviceGroup`): in SDK 9.2.0, 75 products are at API 5.1 or newer (8 at 5.1, 29 at 5.2, 38 at 6.0): 66 watch-type products plus 8 Edge and the eTrex Touch. Examples at 5.1+: fēnix 7/7 Pro/8/9 families, epix Gen 2, FR165/255/265/955/965/970/570/70/170, Venu 3/4/X1, vívoactive 5/6, Instinct 3 / E / Crossover AMOLED, MARQ Gen 2, Approach S50/S70, Descent G2/Mk3, Enduro 3, D2 Mach 1/2, fēnix E. Watches below 5.1 (still with `Weather` from 3.2) get no UV or cloud cover: for example Venu 2 family, Venu Sq 2 and D2 Air X10 (5.0), FR945/745/245 and fēnix 6 (3.x). [SDK data: Devices/*/compiler.json, e.g. fr965](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Devices/fr965/compiler.json) (FR965 = "API level 5.2", `partNumbers[].connectIQVersion` 5.2.0)
- `Weather` is not in Garmin's list of permissions: the Manifest and Permissions table has no Weather row, and `projectInfo.xml` has no Weather permission. [SDK doc: Manifest File and Permissions](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Manifest_and_Permissions.html); [SDK data: projectInfo.xml](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/bin/projectInfo.xml)
- The only permission-gated Weather fields are the location ones: "`observationLocationPosition`: Location where the conditions were observed. If the app does not have the position permission then this will be null"; the deprecated `observationLocationName` is likewise null without the position permission and "may be removed after System 11". [SDK doc: CurrentConditions](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather/CurrentConditions.html)
- Studio's compiler check on TwoSuns: `Toybox.Weather` needs no permission to compile. [Studio: TwoSuns ADR-022 text in decisions.md](file:///Users/mbp/dev/garmin/TwoSuns/docs/decisions.md)
- All `CurrentConditions` members are "or Null"; getCurrentConditions "Get the most recently cached weather conditions … or null if no data is available". The API only reads a device-side cache; it never triggers a fetch. [SDK doc: Toybox.Weather](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html); [Forum: CIQ 3.2 GetCurrentWeather](https://forums.garmin.com/developer/connect-iq/f/discussion/260036/ciq-3-2-getcurrentweather) (forum: update roughly every 20 min on Android, hourly on iOS; null-check everything)
- On the owner's FR965 (API 5.2): the hourly list had 12 entries, 60 minutes apart, first at the current hour; the daily list had 5 entries stamped at local midnight; observation was 18–20 minutes old; weather was re-issued about hourly; the list moved from a 21:00 to a 22:00 start in one step. UV and cloud-cover values were not recorded in those probes. [Studio device: TwoSuns ADR-022 evidence](file:///Users/mbp/dev/garmin/TwoSuns/docs/decisions.md)
- Studio's DayArc already treats UV as a graceful-hide bonus field (`has :uvIndex` guard, API 5.1.0) and corrected an earlier wrong claim that it fell within a 4.2.0 floor. [Studio: DayArc ADR-005](file:///Users/mbp/dev/garmin/DayArc/docs/decisions.md)
- `System.Stats.solarIntensity` (0–100, API 3.2.0) describes "the solar sensor's charge efficiency"; null if the device has no solar, negative when not charging. It is the only light-related reading in the SDK. [SDK doc: System.Stats](https://developer.garmin.com/connect-iq/api-docs/Toybox/System/Stats.html)

### Inferences
- A Vitamin-D window design that wants UV/cloud as inputs must set `minApiLevel` to 5.1 (or use `has :uvIndex` guards on a lower floor) and accept that the reach is the 66 watch products at 5.1+; precipitation chance and condition alone work down to API 3.2.
- Treat UV and cloud cover as best-effort inputs that can be null per device, per region and per sync, not as a guaranteed baseline. No source shows which 5.1+ watches really fill them.
- Hourly `uvIndex` is the useful input for "when is UV high enough"; the daily forecast cannot carry UV, so tomorrow's UV needs hourly entries that reach tomorrow (the FR965 list reaches about 12 hours only).
- `solarIntensity` is a measure of sunlight hitting the watch's solar lens and only exists on solar watches, so it could at most be a bonus "you are in sun now" signal; it is not UV and not exposure time.

### Gaps
- No real-device evidence that `uvIndex` or `cloudCover` are non-null on any watch (the studio's FR965 probes did not log them; DayArc is simulator-only). The forum search for real-device UV null reports returned nothing relevant.
- No source states Garmin's UV scale handling (0–10 documented; real UV can exceed 10, and DayArc's own plan mentions a "UV 11" fit case), or whether UV is the clear-sky or cloud-adjusted value.
- Weather update cadence, how stale a cache can be, and behaviour with no phone are only forum-grade; no Garmin statement found.
- The exact list of 5.1+ watch products that is relevant to a store listing should be read from the upload form's Compatible Devices list (the studio's own `.iq` export count is known to differ from the manifest).

## 2. Background ServiceDelegate (temporal event): what can it read, what is "permitted in background", limits

### Takeaway
A `ServiceDelegate.onTemporalEvent()` can run every 5 minutes at most and may read `Weather`, `ActivityMonitor`, `Activity`/`Position`, `UserProfile`, `SensorHistory`, `Storage` and `Notifications` according to the compiler's scope model (none of these is flagged `disableBackground`); modules flagged as NOT usable in background are `Attention`, `Timer`, `PersistedContent`, `FitContributor`, `ActivityPrompts` and `PersistedLocations`. The SDK docs do not carry a per-API "permitted in background" annotation; the authoritative per-module scope data is the compiler's `api.mir`, and nothing here has run in a background process on a watch.

### Cited Findings
- Background services: "Services may be terminated at any time [to] free memory for foreground applications. Services will also be terminated automatically if they do not exit properly within 30 seconds of opening." "Background services are allowed to run at any time, including while the user is in an activity", so their memory pool is much smaller than the app's. Only code decorated with `:background` (including the `AppBase` class) is compiled into the service. "Modules available to background processes differ from those of their parent application." [SDK doc: Background Services](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Backgrounding.html)
- The type checker "attempts to validate that any member fetched from a module or class is available in all of the same application scopes as the caller"; `:typecheck(disableBackgroundCheck)` turns it off. [SDK doc: Monkey Types](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Monkey_C/Monkey_Types.html) This is the "permitted in background" mechanism; it is driven by flags in the API model.
- The API model flags (read from `api.mir`): modules with `disableBackground = true`: `Attention` (vibrate, tones, backlight, flashlight), `Timer`, `PersistedContent`, `FitContributor`, `ActivityPrompts`, `PersistedLocations`, and the `System.Intent` class. `Graphics` and `WatchUi` carry `disableBackgroundBeforeVersion = "5.1.0"` (usable in background only from 5.1). Not flagged `disableBackground` (so allowed in background by the compiler): `Weather` (and its classes and the `uvIndex`/`cloudCover` members), `ActivityMonitor` (and `Info.moveBarLevel`), `Activity`, `Position`, `SensorHistory`, `UserProfile`, `Application.Storage`, `Background` (including `requestApplicationWake`), `Notifications`, `Time`, `System`, `Lang`, `Complications`, `Communications` (flagged only `disableWatchFace`). A script scanned every member with a `disableBackground` flag; none exists inside the unflagged modules apart from the `Intent` class. [SDK data: api.mir](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/bin/api.mir)
- `Attention.vibrate` and `Attention.playTone` are `disableBackground`: a background process cannot vibrate or beep itself (consistent with forum: "the only way to alert users from a background process is requestApplicationWake"). [SDK data: api.mir](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/bin/api.mir); [Forum: Alert from an app when it's closed](https://forums.garmin.com/developer/connect-iq/f/discussion/272289/alert-from-an-app-when-it-s-closed)
- `Application.Storage` can be written from a background process since API 3.2.0 (`setValue`, `deleteValue`); `AppBase.onStorageChanged()` fires in the other process if both are active. `Application.Properties.setValue` is documented as: "Background processes cannot save Application Properties". [SDK doc: Persisting Data](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Persisting_Data.html); [SDK doc: Properties](https://developer.garmin.com/connect-iq/api-docs/Toybox/Application/Properties.html)
- `Background.exit(data)` hands up to about 8 KB (`ExitDataSizeLimitException`) to the foreground `onBackgroundData()`; `getBackgroundData()` returns null in the main process. [SDK doc: Toybox.Background](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html)
- `registerForTemporalEvent(Moment | Duration)`: "Temporal events cannot be set to occur less than 5 minutes after the last temporal event occurred. For watch-apps and widgets the 5 minute restriction is cleared on application startup if the event was specified using a Moment." Only one temporal event may be registered; a Moment in the past fires immediately. Other triggers: sleep time, wake time, every 1000 steps (device-recorded steps only), goal reached, activity completed. [SDK doc: Toybox.Background](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html); [SDK doc: Background Services](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Backgrounding.html)
- Per-device background memory limit (device data): 65,536 bytes on 63 of the 66 watch device ids at API 5.1+ (the 66 = 63 + 3; this 63 is unrelated to HeroSet's "63 of 80"); 32,768 bytes on the 3 device ids `instinct3solar45mm` (Instinct 3 Solar 45/50 mm), `instincte40mm`, `instincte45mm` (4 product SKUs by size; these also have a 32 KB glance and a 128 KB watch-app limit) and on the 8 Edge units and eTrex Touch. [SDK data: compiler.json files](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Devices/fr965/compiler.json) (FR965: background 65,536; glance 65,536; watchApp 786,432)
- Garmin's own FAQ sample says background services have a "32 KB heap" (older text). [SDK doc: FAQ background service](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Connect_IQ_FAQ/How_Do_I_Create_a_Connect_IQ_Background_Service.html) (conflicts with the 64 KB device data; device data wins on the newer watches).
- Garmin's own Notifications sample is a `watch-app` with permissions `Background` and `Notifications`, registers a temporal event in `onStart`, and calls `Notifications.showNotification(...)` from a `(:background)` `ServiceDelegate.onTemporalEvent`. [SDK data: samples/Notifications manifest.xml](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/samples/Notifications/manifest.xml); [SDK data: BackgroundDelegate.mc](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/samples/Notifications/source/BackgroundDelegate.mc)
- A background process registered by a widget keeps running when the widget is closed ("the background will run as soon as you exit the device app"; a running device app blocks background runs until it exits). [Forum: Background widget](https://forums.garmin.com/developer/connect-iq/f/discussion/171632/background-widget/928434) (forum-grade)
- An unresolved 2026 forum report: on an Epix 2 Pro 47mm with SDK 8.3.0, a **watch-app** registered a temporal event with no exception but `onTemporalEvent` never fired on the real device (it fired when simulated); a respondent said their watch face runs a 5-minute background fine. No fix found in the thread. [Forum: Background temporal events never fire](https://forums.garmin.com/developer/connect-iq/f/discussion/440376/background-temporal-events-never-fire-registerfortemporalevent-silently-ignored) (forum-grade, one thread)
- The studio's faces read `Weather` and `ActivityMonitor` in the foreground only (see their ADRs); no studio or forum source I read shows `Weather.getCurrentConditions()` or `ActivityMonitor.getInfo()` called from a background process on a watch (forum weather threads that mention a background process are about fetching weather from the web, a different case). [Studio: TwoSuns ADR-022](file:///Users/mbp/dev/garmin/TwoSuns/docs/decisions.md)

### Inferences
- Per the compiler's scope model, a temporal-event delegate can read Weather, ActivityMonitor, Activity.getActivityInfo, SensorHistory, UserProfile and Storage, and can show a Notification or request an app wake. This is a compile-time permission, not proof that every call returns data in a background process on a watch.
- The robust pattern is: the background process reads, decides, writes small values to `Storage`, and then either calls `Notifications.showNotification` (watch-app) or `requestApplicationWake`. The glance/foreground then reads Storage. Writing Storage from the background (3.2.0+) is simpler than relying on `onBackgroundData`, which only reaches the foreground app.
- Vibration of the user must come from the system notification/wake UI, because `Attention` is closed to the background process.
- Everything must fit in 30 seconds and in 64 KB (32 KB on the 3 Instinct device ids, 4 SKUs by size); a hand-rolled solar-elevation calculation is cheap, but Weather objects plus Storage plus Notification resources all have to be `:background`-scoped.

### Gaps
- No Garmin source states per-API background availability in prose; the only primary evidence is `api.mir` scope flags. A test compile of a `(:background)` delegate at `--typecheck 3` would confirm it, and a real watch run is needed to confirm data is returned (Weather cache and Position in a background process).
- Whether `Position.getInfo()` works in a background process on a real watch (and returns a cached fix) is unknown; the compiler allows it.
- The reliability of temporal events for watch-app type on current firmware is contradicted by one forum report versus Garmin's own sample; nothing settles it without a watch test.
- The 5-minute minimum is documented; no Garmin source gives the actual jitter or how the scheduler behaves in low battery or sleep.

## 3. Inactivity detection: ActivityMonitor.Info fields and what is realistic

### Takeaway
`ActivityMonitor.Info` has no "time since last move" field. The available signals are `moveBarLevel` (0–5), the cumulative `steps` since midnight, `stepGoal`, `timeToRecovery` (hours), `activeMinutesDay`, `stressScore` and a heart-rate history iterator. The realistic way to detect "inactive too long" is to compare step counts between background runs and/or read `moveBarLevel`, with no Garmin guarantee on update cadence.

### Cited Findings
- `ActivityMonitor.Info` members (current day from midnight): `steps`, `stepGoal`, `moveBarLevel`, `timeToRecovery` (hours, API 3.3.0), `activeMinutesDay`/`activeMinutesWeek`/`activeMinutesWeekGoal` (2.1.0), `calories`, `distance` (cm), `floorsClimbed`/`floorsDescended`/`metersClimbed` etc., `respirationRate` (3.3.0), `stressScore` (5.0.0, rolling 30-second average), `pushes`/`pushGoal`/`pushDistance` (wheelchair, 4.2.x); `isSleepMode` is deprecated. All are "or Null". There is no field for last movement time, idle time or sedentary duration. [SDK doc: ActivityMonitor.Info](https://developer.garmin.com/connect-iq/api-docs/Toybox/ActivityMonitor/Info.html); [SDK doc: Quantifying User Information](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Quantifying_the_User.html)
- `moveBarLevel` is "between `MOVE_BAR_LEVEL_MIN` and `MOVE_BAR_LEVEL_MAX`", and those constants are 0 and 5. [SDK doc: Toybox.ActivityMonitor](https://developer.garmin.com/connect-iq/api-docs/Toybox/ActivityMonitor.html)
- The meaning of the levels (0 none; 1 = one hour of inactivity; levels 2–5 add one segment per 15 minutes) is stated only in a forum post. [Forum: How to display MovementBar in Watchface](https://forums.garmin.com/developer/connect-iq/f/discussion/5379/how-to-display-movementbar-in-watchface) (forum-grade; same thread says nothing on reset behaviour or background access)
- When wheelchair mode is on, `Info.steps`, `stepGoal` and floors are zero and `pushes`/`pushGoal` carry the values. [SDK doc: Quantifying User Information](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Quantifying_the_User.html)
- `ActivityMonitor.getHeartRateHistory(period, newestFirst)` returns an iterator of HR samples "up to the last power cycle", sample spacing device-dependent; `ActivityMonitor.getHistory()` returns at most 7 daily objects (steps, stepGoal, calories ...), not intraday. [SDK doc: Toybox.ActivityMonitor](https://developer.garmin.com/connect-iq/api-docs/Toybox/ActivityMonitor.html)
- A background step trigger exists: `registerForStepsEvent` wakes the service "each time a multiple of 1000 steps is reached", only for device-recorded steps. [SDK doc: Toybox.Background](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html)
- A 2026 forum thread reports `ActivityMonitor.Info.steps` appearing to update only about once a minute on some real watches in a watch face (no Garmin reply). [Forum: ActivityMonitor.Info.steps update cadence](https://forums.garmin.com/developer/connect-iq/f/discussion/439177/activitymonitor-info-steps-update-cadence-in-watch-faces) (forum-grade, unresolved)
- `UserProfile.Profile.sleepTime` / `wakeTime` (API 1.0.0) and `upcomingSleepTime` / `upcomingWakeTime` (added in SDK 9.1.0) exist for quiet-hour logic; background `registerForSleepEvent` / `registerForWakeEvent` are also available. [SDK doc: Quantifying User Information](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Quantifying_the_User.html); [SDK doc: Release Notes](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Readme/History.html)

### Inferences
- Option A (move bar): `moveBarLevel >= 1` is a Garmin-computed "has been still about an hour" flag (if the forum meaning is right). Cheap, one read per background run, but the semantics are not documented by Garmin and it may only mean "move alert pending".
- Option B (step delta): store `(timestamp, steps)` in `Storage` at each background run; "inactive" = delta below a threshold over N minutes. Works with a 5-minute cadence; fails on wheelchair users unless `pushes` is substituted, and on steps-only blind spots (cycling, sitting with a drink).
- Neither detects "indoors vs outdoors", so an "inactive" test is a proxy for "not going outside", not for sun exposure. Quiet hours can use sleep/wake time from UserProfile.
- For the Vitamin-D use case, "inactive for the whole window" is better read as "few steps in the last 60–90 minutes during daylight", which Option B can express.

### Gaps
- No primary source defines the update cadence or exact semantics of `moveBarLevel`, nor how fresh `steps` is in a background process (only one forum thread, which is about watch faces).
- No evidence either way that `ActivityMonitor.getInfo()` returns live values in a background process on a real watch.
- Whether the move bar is silenced by DND, sleep, or a "Move alert" user setting being off is not documented.

## 4. Nudging: Background.requestApplicationWake and the Notifications module

### Takeaway
`Background.requestApplicationWake(message)` (API 2.3.0) shows a confirmation dialog asking the user to open the app and is valid only for widget or device-app background tasks (ignored by watch faces); `Notifications.showNotification` (API 5.1.0, needs the `Notifications` permission, which `projectInfo.xml` does not allow for the `widget` app type) is the newer, richer nudge and Garmin's sample calls it from a temporal event. Vibration, DND behaviour and frequency limits are not documented by Garmin; forum evidence says wake-prompt behaviour differs widely by device.

### Cited Findings
- `requestApplicationWake(message as String)`: "Display a confirmation dialog requesting to launch the application to which the background task belongs. If the dialog is confirmed, the application will open. If the dialog is declined, the application will not open and the dialog will be dismissed. Message limit 255 bytes (`MessageSizeLimitException`). [SDK doc: Toybox.Background](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html)
- "Background.requestApplicationWake() allows you to interrupt the user to request that they open your application. When called, the user will be presented with a confirmation message of your choice. The system may suppress the request if there are not sufficient resources to launch the app." [SDK doc: Notifications core topic](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Notifications.html)
- It is a background-process API: Garmin's own example calls it inside `onTemporalEvent()` of a `(:background)` delegate, so it fires with the app closed. [SDK doc: Toybox.Background example](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html)

[SDK doc: Notifications core topic](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Notifications.html); [SDK doc: Toybox.Notifications](https://developer.garmin.com/connect-iq/api-docs/Toybox/Notifications.html); [SDK doc: Release Notes](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Readme/History.html)
- Notifications module device list (SDK 9.2.0 page): 57 listed entries (grouped product names), all at API 5.1+, including fēnix 7/8 families, epix Gen 2, FR165/255/265/955/965/970/570, Venu 3/4/X1, vívoactive 5/6, Instinct 3 Solar/AMOLED, Instinct E, Instinct Crossover AMOLED, MARQ Gen 2, Descent G2/Mk3, Enduro 3, Approach S50/S70, Bounce 2, D2 Mach 1/2. - `Notifications` permission is allowed for watchface, datafield and watch-app types in the SDK's own permission map and is absent from the `widget` map; `Background` is allowed in all. [SDK data: projectInfo.xml permissionMaps](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/bin/projectInfo.xml) (the public Manifest and Permissions table does not yet list `Notifications` at all, a documentation gap: [SDK doc](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Manifest_and_Permissions.html))

The thread has no Garmin staff reply and none on DND or rate limits; a poster points to the SDK Notifications sample as the reference. [Forum: New notifications api](https://forums.garmin.com/developer/connect-iq/f/discussion/406092/new-notifications-api) (forum-grade)
- requestApplicationWake on real devices (forum, Garmin forum posts summarised): it "displays a message asking if you want to start the main app, and on some devices vibrate or beep"; one developer says "on some devices it hangs, on some devices there is no vibration accompanied with the message"; another that "the only call that can switch to the app gives a prompt that must be responded to so requires user intervention". - During an activity: a forum respondent states that when the user says yes, "there's not enough memory for the full widget to run … so the activity gets shut down"; another reports the wake prompt appeared during an activity although notifications during activities were disabled, and that temporal notifications respect do-not-disturb/sleep mode in their experience; the poster resolved to check for an ongoing activity before calling the API. [Forum: Background notifications stop ongoing activity](https://forums.garmin.com/developer/connect-iq/f/discussion/239715/background-notifications-stop-ongoing-activity) (forum-grade, from 2019-era thread)

- SDK release note anomaly: v9.1.0 lists "Fix Background.deleteApplicationWakeDismissedEvent() not unregistering for the event", but no `ApplicationWakeDismissed` symbol exists in `api.mir` or in the 9.2.0 API docs, so a dismissed-event API is not documented. [SDK doc: Release Notes](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Readme/History.html)
- The SDK docs contain no frequency limit for `requestApplicationWake` or `showNotification`; the only documented cap is the 5-minute temporal-event floor.

### Inferences
- A "go outside now" nudge has two Garmin-sanctioned forms: (1) `requestApplicationWake` shows a yes/no dialog to open the app (works for widget or watch-app type; behaviour varies by watch); (2) `Notifications.showNotification` on a `watch-app` with the `Notifications` permission on API 5.1+ watches (the same floor as UV/cloud). On the 5.1+ watches that carry UV data, (2) is available on most.
- Because the Notifications permission is not in the `widget` map, a design wanting notifications should be type `watch-app`, consistent with Garmin's own sample. Whether a manifest `widget` on API 4+ is silently built as `watch-app` (HeroSet notes, forum) and thereby accepts `Notifications` was not tested.
- Vibration is not under the app's control in a background process (see section 2), so whether the user feels a buzz depends on the watch's own notification personality and settings. Do not promise a buzz in copy.
- Dismiss/ignore handling: with a wake prompt, declining simply closes the dialog (nothing reaches the app); with a notification, `registerForNotificationMessages` can learn about selection/dismissal in the foreground app. A nudge policy (snooze, daily cap) must therefore be stored by the background process itself.
- Garmin's app review guideline 2a ("do not hurt battery") and the user-trust cost of repeated prompts argue for a hard daily cap and quiet hours even though no API limit exists (studio's policy report cites 2a: [Studio: Garmin policies and design guidelines](file:///Users/mbp/dev/garmin/reports/Garmin%20policies%20and%20design%20guidelines.md)).

### Gaps
- Exact on-watch presentation (prompt text, whether it vibrates, whether it respects Do Not Disturb and sleep mode) is not documented by Garmin; no device evidence in the studio. Needs a watch test per target model, ideally FR965 plus one AMOLED and one MIP.
- No documented rate limit or "system may suppress" criteria beyond "not sufficient resources".
- Whether `requestApplicationWake` works from a `watch-app` as well as a widget on API 5+ watches is stated in the docs ("widget or device app") but not tested by any source found.
- Whether an app launched by the wake dialog has the glance-launch inactivity timeout is unknown (the SDK says an app launched from the glance list times out; launch from the activity menu does not).
- The app review guideline text for notifications/background behaviour could not be retrieved (the review guidelines page rendered as a navigation shell); no source shows how reviewers treat repeated wake prompts.

## 5. Permissions needed and how permissions show in the store listing

### Takeaway
A weather-plus-sun-window app needs no permission for Weather itself; it needs `Background` (temporal events), `Notifications` (if using the notification API), and `Positioning` only if it reads a location (for sun times/elevation) — plus nothing for `ActivityMonitor` or `Storage`. `SensorHistory` and `Communications` are not required for this design. How permissions are shown to the user in the store listing could not be verified from a primary source.

## 6. Glance views, widget vs watch-app type, devices, memory, and reading background-written data

### Takeaway
On API 4.0+ a glance is available to `watch-app` and `widget` apps (an app or widget must implement `getGlanceView` to appear in the glance list); glance memory is 64 KB on 63 of the 66 watch device ids at API 5.1+ (32 KB on the Instinct 3 Solar/Instinct E family); a glance may use Storage and the same modules as the app, so it can show values the background process wrote. The studio's HeroSet glance research already covers the mechanics and pitfalls.

### Cited Findings
- Glances: Since API 3.1.0. "In devices before API level 4.0.0 if a widget doesn't override [getGlanceView], default GlanceView will be used … In API level 4.0.0 and above, apps and widgets must implement a glance view to appear in the glance list." A glance runs with limited memory ("32KB for most devices" per prose); the `:glance` annotation scopes code. "Most functionality supported in Widget is still supported when running as a Glance, such as accessing application storage and making web requests … moving CPU intensive work to a Background service." [SDK doc: Glances](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Glances.html)
- Lifecycle: on devices with ample resources the glance process is kept alive and updated "as needed", under 1 Hz recommended; on low-memory devices the glance runs through a full app lifecycle only when it becomes visible, at least 30 seconds apart, and its rendering is cached. [SDK doc: Glances](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Glances.html)
- Memory by device (data, not prose): `compiler.json` `glance` limit is 65,536 bytes on 63 of the 66 watch device ids at API 5.1+ and 32,768 on the other 3 (`instinct3solar45mm`, `instincte40mm`, `instincte45mm`; 4 SKUs by size); background limit matches. Those 3 also have a 131,072-byte watch-app limit (others 786,432). [SDK data: compiler.json](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Devices/fr965/compiler.json); studio's HeroSet research reached the same conflict between SDK prose (32 KB) and device data (64 KB) and sided with the device data. [Studio: HeroSet glance view research](file:///Users/mbp/dev/garmin/reports/HeroSet%20glance%20view%20research.md)
- `Application.Storage` written from the background process is readable in the foreground process; `onStorageChanged()` notifies the other process. Glances may call `Application.Storage`. [SDK doc: Persisting Data](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Persisting_Data.html); [SDK doc: Glances](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Glances.html)
- App types: five (`watchface`, `datafield`, `widget`, `watch-app`, `audio-content-provider-app`). "On devices after API 4.0.0, widgets are now from the app launcher, and apps can have glances … If you are building an app, creating a glance for your application gives users two unique ways to launch your app." [SDK doc: Manifest File and Permissions](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Manifest_and_Permissions.html); [SDK doc: Application and System Modules](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Application_and_System_Modules.html)
- "If an app is launched from the glance list, a timeout will be applied to the app. If the user does not exit the app within a given time frame, the system will terminate the app and return to the home screen. If an app is launched from the activity menu, however, it will not time out." Launch source is detectable via `state[:launchedFromGlance]`. [SDK doc: Application and System Modules](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Application_and_System_Modules.html)
- Studio, from the HeroSet research: a manifest `widget` on CIQ 4+ is built as a watch-app (forum bug report); `AppBase` is always loaded whole into the glance process so the app class must not do foreground work; glance-scope mistakes compile clean at the default level and fail only at runtime (`-l 2` warns, `-l 3` errors); resources need `scope="glance"`; glance renders on a clipped rectangle; glance code was measured at about 6.9 KB of 64 KB for HeroSet; nothing ran in glance mode in the simulator or on a watch. [Studio: HeroSet glance view research](file:///Users/mbp/dev/garmin/reports/HeroSet%20glance%20view%20research.md)
- Live updates for the 66: `simulator.json` has `liveUpdates: true` for all 66 watch device ids at API 5.1+ (script over `Devices/*/simulator.json`; a different, larger set than HeroSet's own 63-of-80 below). [SDK data: simulator.json files](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Devices/fr965/simulator.json)
- Studio, same report: HeroSet's own manifest has 63 of its 80 products getting a glance (CIQ 5.0 or newer; a different count from the 63 above), all with live updates; the 17 CIQ 3.4 products ignore `(:glance)` with a warning. [Studio: HeroSet glance view research](file:///Users/mbp/dev/garmin/reports/HeroSet%20glance%20view%20research.md)
- Device-specific glance quirks (fēnix 8 flashes a grey rectangle for 1–2 s; clipped left edges on round bezels; transparent background required) are forum-sourced in the studio report; the simulator's glance mode could not be scripted. [Studio: HeroSet glance view research](file:///Users/mbp/dev/garmin/reports/HeroSet%20glance%20view%20research.md)

### Inferences
- The right shape for a Vitamin-D app is a `watch-app` (to hold `Notifications` and `Background`) with a read-only glance reading Storage keys that the background process wrote (window state, minutes left, UV now). This needs the glance-process hygiene HeroSet found (lazy app-object initialisation, `scope="glance"` strings).
- Glance reads at draw time must be date-safe: a glance can outlive midnight, so a stored "window ends 14:20" should carry its own date or timestamp (HeroSet's stale-day lesson).
- Because UV/cloud need API 5.1+ and every 5.1+ watch device id has live-update glances (device data above), with 64 KB on 63 of the 66 (32 KB on the 3 Instinct ids), the glance floor is not the binding constraint; the Instinct 32 KB parts need a lean glance or no glance.
- The launch-from-glance timeout means a long interactive session after tapping the glance may be terminated; a sun-window app has short sessions, so this matters little (HeroSet's rep-counting is the worst case; not ours).

### Gaps
- No glance has run on a watch for any studio app; all glance claims are compile/simulator-grade.
- Whether the glance process shares Storage consistently with a concurrently running background process is undocumented beyond `onStorageChanged`.
- Whether `type="widget"` accepts `Notifications` on API 5+ devices (if built as watch-app) is untested; `projectInfo.xml` says the widget map lacks it.

## 7. Battery and timing of background work

### Takeaway
Garmin documents the 5-minute floor and the 30-second kill but gives no quantitative battery cost for temporal events; the only Garmin-side battery rule found is the review guideline "do not hurt battery" (via the studio's policy report). A watch app should therefore run the minimum useful cadence and exit fast.

### Cited Findings
- Temporal events cannot be less than 5 minutes after the last event; a background service must exit within 30 seconds or is terminated; services "may be terminated at any time" to free memory. [SDK doc: Toybox.Background](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html); [SDK doc: Background Services](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Backgrounding.html)
- `getLastTemporalEventTime()` supports "ensuring new events are not scheduled within the five minute minimum"; `getLastTemporalEventTime` returns null if the app has started since the last event. [SDK doc: Toybox.Background](https://developer.garmin.com/connect-iq/api-docs/Toybox/Background.html)
- Garmin offers event-driven alternatives to polling: sleep/wake events, steps events (every 1000 steps), goal events. [SDK doc: Background Services](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Backgrounding.html)
- The studio's policy report records review guideline 2a "do not hurt battery" and notes there is no numeric power budget published. [Studio: Garmin policies and design guidelines](file:///Users/mbp/dev/garmin/reports/Garmin%20policies%20and%20design%20guidelines.md)
- The studio's face-market research states background runs at most every 5 minutes with about 32 KB and about 30 s limits (older, forum-sourced). [Studio: platform_constraints_monetization.md](file:///Users/mbp/dev/garmin/research_notes/Garmin%20watch%20face%20market%20gap/platform_constraints_monetization.md)
- Temporal events for other apps do not run while a device app is open; they resume on exit. [Forum: Background widget](https://forums.garmin.com/developer/connect-iq/f/discussion/171632/background-widget/928434) (forum-grade)

### Inferences
- Reading cached Weather, ActivityMonitor and Storage and computing sun position costs very little CPU; the dominant costs are the wake-up itself and any BLE/web work, which this design does not use (no `Communications`). A 5- to 15-minute cadence with a quiet-hours gate (sleep/wake time) is reasonable.
- Registering a `Moment` at the next event of interest (for example, sunrise plus offset, window start) instead of a fixed 5-minute loop would reduce wake-ups; the 5-minute floor still applies.
- Do not make claims about "battery impact" in store copy without a measured wear-day comparison.

### Gaps
- No Garmin-published battery figures, and no studio measurement. The studio's all-day dev-build wear (owner) is the right instrument, and a day with/without the background registered is the comparison.
- The App Review Guidelines text itself (battery criteria for background apps) could not be retrieved.

## 8. Sun position: sunrise/sunset APIs, built-in sun elevation, and offline location sources

### Takeaway
`Weather.getSunrise(location, date)` and `getSunset(location, date)` exist (API 3.3.0) but need a `Position.Location`; there is no sun elevation/azimuth/UV-clear-sky API in the SDK, so solar elevation must be calculated from date, time and latitude/longitude. Garmin's own sunrise/sunset Complications need no location but only a watch face can subscribe. A usable location in a watch-app comes from `Position.getInfo()` (with `Positioning`) or a saved place; `Activity.currentLocation` and the Weather observation location were null on the owner's FR965.

### Cited Findings
- `Weather.getSunrise(location as Position.Location, date as Time.Moment)` and `getSunset` return `Time.Moment or Null` ("null if no sunrise/sunset time is available"), Since API 3.3.0; the supported-device list differs from the Weather module's (it adds the fēnix 5 Plus family and omits, for example, GPSMAP 67, Montana 7, D2 Air, vívoactive 3 Music and Edge 1030/Bontrager). [SDK doc: Toybox.Weather](https://developer.garmin.com/connect-iq/api-docs/Toybox/Weather.html)
- A search of the SDK docs for sun elevation, sun position, solar elevation, solar angle, solar intensity history and UV returned only: Weather `uvIndex`, Complications `SUNRISE`/`SUNSET`, and `System.Stats.solarIntensity` (charging efficiency). `SensorHistory` offers body battery, heart rate, temperature, pressure, elevation, oxygen saturation and stress history only. [SDK doc: Toybox.Complications](https://developer.garmin.com/connect-iq/api-docs/Toybox/Complications.html); [SDK doc: Quantifying User Information](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/doc/docs/Core_Topics/Quantifying_the_User.html); [SDK data: api.debug.xml](file:///Users/mbp/Library/Application%20Support/Garmin/ConnectIQ/Sdks/connectiq-sdk-mac-9.2.0-2026-06-09-92a1605b2/bin/api.debug.xml) (grep of every `get*History` symbol)
- `Complications.COMPLICATION_TYPE_SUNRISE` and `_SUNSET` (API 4.2.0) are non-negative Numbers: seconds since local midnight; they need no location. The `ComplicationSubscriber` permission is allowed for watch faces only (docs table and `projectInfo.xml`); the watch-app map carries `ComplicationPublisher` instead. ### Inferences
- Solar elevation therefore has to be coded: a standard solar-position algorithm (declination and equation of time from the day of year, hour angle from local solar time) needs only latitude, longitude, the date and the UTC time. Cheap enough for the background process; a separate researcher in this effort has fixtures for that (`solar_elevation_fixtures.py`), and the formula itself was not researched here.
- Offline location for a watch-app: call `Position.getInfo()` when the app is in the foreground (with `Positioning`), store a place rounded to about 0.1 degree in `Storage` (the studio's own pattern), and let the background process read that stored place; do not rely on `Activity.currentLocation` or the Weather observation location. The background process calling `Position.getInfo()` itself is allowed by the compiler but unproven on a watch.
- A no-location variant could rely on `Weather.getSunrise/getSunset` only if a location exists, so it still needs Positioning; a user-set "city/latitude" setting is the only permission-free alternative, with an accuracy and UX cost.
- Whether the "vitamin D window" cares about UV >= 3 and sun elevation is a product decision for other researchers; the platform gives hourly UV on 5.1+ watches and solar elevation by computation.

### Gaps
- No confirmation that `Position.getInfo()` returns a usable fix to a watch-app on watches other than the FR965, or in a background process; M3/M4 location probes were never run.
- `Weather.getSunrise` on a real watch (day boundary, polar cases returning null) is unverified; the studio's evidence is simulator-grade.
- The exact device list difference between `Weather` and `getSunrise` (documented as shorter) was not tabulated against the 5.1+ watch list.
- I found no Garmin statement on whether any Garmin first-party UV or "sun exposure" data is exposed to Connect IQ besides the Weather `uvIndex`.
