# Three Verden codebases need tightening, not rewriting

All three projects are in good shape, and the architecture of each is right for its job. None of them needs a restructure. What remains is a short list of hardening fixes, contract documentation that has fallen behind the code, and doc drift. **HeroSet** has clean, well-tested domain and data layers: 95 dev tests in the working tree, Storage isolated behind one seam, and complete ADR-048 tap guards on every custom commit screen. Its real risks are a `Complications.updateComplication` call with no catch that runs on every launch, untyped members that switch off the compiler on the persistence path, and a write-failure flag that later writes can clear. **HeroFace** is small and disciplined. Its contract parser rejects any value it cannot trust, and its render path does little work. The one potentially serious risk is unverified: its always-on screen may break the original Venu's 3-minute pixel rule on 3 of 117 products. It also has a nullable complication id passed straight into a system call at launch, a settings option that does nothing, and heavy doc drift. **The Verden website** builds cleanly, passes strict `tsc`, and ships zero client JavaScript. The urgent item there is a timing hazard, not a code bug: the **staged HeroSet pages advertise 80 watches**, but the 13 touch-first models are not yet in a store build, and every push to `main` deploys. After that come a desktop layout bug on `/heroface/`, missing canonical and OG metadata while a duplicate host is live, and an auto-playing animation with no pause control. Most fixes are under 15 lines. Nothing in this review ran on a watch.

The evidence is four static reviewer notes plus facts the coordinator verified in this session. The reviewers read every source file, compiled with `monkeyc` at type-check levels 0 to 3, read SDK 9.2.0 docs and simulator device definitions, built the website, and made read-only `curl` requests to the live site. Citations point at files in the working tree as of 2026-09-24.

## Verdict per project: sound foundations, and each project has one or two real hazards

**HeroSet: good, with the risk sitting at the edges.** The core layers show no likely crash. The domain code (rules, calendar, detector, swing trace, learner) is typed, short and well covered: rules has 23 tests, calendar 12, store 24, detector 8, learner 7 with timing bounds, and sync 7 ([HeroSetStoreTest.mc](/Users/mbp/dev/garmin/HeroSet/source/test/HeroSetStoreTest.mc), [HeroSetRepCounterTest.mc](/Users/mbp/dev/garmin/HeroSet/source/test/HeroSetRepCounterTest.mc)). Only [HeroSetPersistentStorage.mc:15,19](/Users/mbp/dev/garmin/HeroSet/source/data/HeroSetPersistentStorage.mc) touches `Storage`. The dev build, the store build and the store test build all compile for fr965, fenix6 and venu441mm. The `(:sync)`/`(:debug)` split keeps Fit and the test hooks out of the store build ([store.jungle](/Users/mbp/dev/garmin/HeroSet/store.jungle)). The UI layer is equally disciplined. Every text draw goes through `HeroSetDraw.text` ([HeroSetDraw.mc:20](/Users/mbp/dev/garmin/HeroSet/source/ui/HeroSetDraw.mc)). No file is over 250 lines. Pop counts match ADR-024 on every path, and all three save methods are idempotent through `_saved`. What undercuts this is a set of issues that tend to fail only on a device: the uncaught complication throw, untyped `_storage`/`_clock`/`_store` members, a storage seam typed `Lang.Object` that would compile the ADR-022 Symbol crash, a dashboard START that does nothing on d2airx10, and architecture docs that still say "touch-first interaction" is out of scope. At `-l 3` there are **197 strict-typecheck errors**, about 160 of them in the UI. Many are false-positive narrowing complaints, so they are not a to-do list.

**HeroFace: good, with one open device question.** State is rebuilt once a minute and invalidated by the link version ([HeroFaceView.mc:72-83](/Users/mbp/dev/garmin/heroFace/source/HeroFaceView.mc)). The partial update is clip, clear, one `drawText`, unclip ([HeroFaceView.mc:99-110](/Users/mbp/dev/garmin/heroFace/source/HeroFaceView.mc)). Every API above CIQ 3.0 sits behind `has`. The contract consumer matches HeroSet's 10-field publisher index for index ([HeroFaceContract.mc:35-47](/Users/mbp/dev/garmin/heroFace/source/HeroFaceContract.mc), [HeroSetComplicationPublisher.mc:38-49](/Users/mbp/dev/garmin/HeroSet/source/app/HeroSetComplicationPublisher.mc)). The weak points are the always-on walk, which stays inside an 8 × 8 px box and moves on y only every 3 minutes ([HeroFaceSleep.mc:16-18](/Users/mbp/dev/garmin/heroFace/source/HeroFaceSleep.mc)), the link discovered only at `onStart`, and docs (`plan.md`, `compatibility.md`, `go-to-market.md`) that contradict the live state of the product. The project builds clean at `-l 2`. At `-l 3` it has only 5 errors, and 2 of them (the nullable id) are real.

**Verden website: very good architecture, with claim hygiene the main risk.** `npm run build` prerenders 7 routes plus `404.html`, and none of them contains a `<script>` ([prerender.ts:13-16](/Users/mbp/dev/garmin/verden-site/prerender.ts)). Routes, nav, home and 404 all come from one app registry ([src/apps/index.ts](/Users/mbp/dev/garmin/verden-site/src/apps/index.ts)). `npm audit` finds 0 vulnerabilities. Contrast tokens pass AA. Live trailing-slash URLs 301 correctly. The defects are in what the pages claim relative to the watch docs, plus a few CSS, head-metadata and accessibility gaps. About 60 lines are copy-pasted between the two app folders.

Severity means: **High** = likely user-visible failure, a store-rule breach, or a false public claim. **Medium** = a real defect or rule violation with a plausible way to fail. **Low** = hygiene, tests or docs.

## Decisions the owner has to make before a fixer can act

Four items have more than one reasonable answer, so a fixer should not pick one alone.

**Quick-save semantics (HeroSet F2).** When the learner drops a lone rep as "getting up", the workout's Back gate still opens the save menu, because it checks `getDetectedCount() > 0`. The menu then reads "0 reps", and Save banks nothing with no toast ([HeroSetWorkoutDelegate.mc:40-47](/Users/mbp/dev/garmin/HeroSet/source/ui/workout/HeroSetWorkoutDelegate.mc)). The gate's own comment says a lone rep "is still movement the user may want to keep", so the code contradicts its stated intent. Option (a) gates Back on `getCount() > 0`. That is one line and matches what Save already does. Option (b) keeps the gate and has quick-save bank the detected count when the dropped count is 0. Option (a) is safer for learner data; option (b) respects the user's explicit Save. Either way, add a test and fix the input-and-ux wording (S19).

**HeroFace blue versus studio blue.** HeroFace's field color `#55aaff` and the studio's `#62b0ea` have a **1.04:1** contrast ratio, so they read as the same color. DESIGN.md requires that visitors can "tell which event they are in from the color alone" ([DESIGN.md:126](/Users/mbp/dev/garmin/verden-site/DESIGN.md)), and the home page stacks the two directly. HeroFace's blue mirrors the watch palette (`ACCENTS[0] == EFFORT`), so re-keying the studio color is likely the cheaper move. Whichever you choose, add `heroface-*` tokens to DESIGN.md.

**WCAG pause control for the RepCounter.** The three hero counters animate for about 27 s, 55 s and 20 s ([global.css:185-190](/Users/mbp/dev/garmin/verden-site/src/styles/global.css)). WCAG 2.2 SC 2.2.2 (Level A) requires a pause, stop or hide mechanism for auto-starting motion that lasts more than 5 s and runs alongside other content ([W3C Understanding 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)). Gating on `prefers-reduced-motion` is good, but it does not satisfy that criterion on its own. Both zero-JS fixes work: start the counts near 100 so each run is 5 s or less, or add a CSS-only checkbox toggle with `:has(#pause:checked)`. The first changes the look and the second adds a control, which makes this a design call. Note that the reviewer's reading of the success criterion as applying to `aria-hidden` decorative figures is an interpretation.

**Native exit-menu ordering on touch watches.** `ManualExitMenu` defaults its focus to Save, while `WorkoutEndMenu` defaults to the safe Resume ([manual_exit_menu.xml](/Users/mbp/dev/garmin/HeroSet/resources/menus/manual_exit_menu.xml)). ADR-048 deliberately accepts tap-selectable native menus. Reorder to Keep Editing/Save/Discard only if Venu owners report mis-taps.

## What must not be churned

The reviews agree on one thing: the good parts of these codebases are load-bearing, and "simplifying" them would bring back bugs the ADRs already paid to remove. **In HeroSet**, keep these as they are:

- **Storage and clock seams.** Only `HeroSetPersistentStorage` touches Storage, and `HeroSetStorage`/`HeroSetClock` injection is what lets 24 store tests run the real code.
- **Fixed key spellings and no Symbols in Storage.** `exerciseKeyString` throws on an unknown exercise, and `hero_learning` uses string keys.
- **`asNumber`/`asNumberOrNull` narrowing** (ADR-019).
- **The XP ratchet** capped at a fixed 100 reps and written credit-before-XP. Do not reorder it, because reversing the order re-pays XP on retry (ADR-002).
- **Calendar-day keys with no epoch math.**
- **The streamed swing trace and the memoised threshold grid** (ADR-046). Do not "simplify" them back to a replay.
- **The same-name `(:sync)`/`(:nosync)` coordinator twins.**
- **`method(:onSensorData)` on a public method** (ADR-023), and the untyped accelerometer arrays behind `instanceof` guards (ADR-022).

- **`onSelect` returning false on commit screens.** Per the SDK, returning true would swallow START. `HeroSetInputTest` pins this.

- **The version-1, append-only complication format.**

**In HeroFace**, keep these as they are:

## Limits of this review

This was a static review. **Nothing ran on a watch.** No monkeydo or simulator test run was part of the four notes, so their coverage statements are static counts. The only runtime evidence comes from the coordinator's own sweep (95 dev PASSED lines, store count pending) and the per-language fit run. The d2airx10 START finding rests on the **simulator key map**, and the real watch's button mapping could differ. The same caveat applies to every simulator result cited here: **passing in the simulator is not proof on a device**. ADR-048 still owes an on-wrist check of the FR965 START path after the `onSelect`→`onKey` move and a manual tap/swipe check on a touch-first watch. HeroFace's original-Venu burn-in risk, the uninstall and install-while-running link paths, peak memory on a 96 KB product, and partial-update cost are all unmeasured. The website was rendered only in dark mode at 1400 px, with no Lighthouse or axe run, and the live store device lists were not checked against the claimed 67. The `-l 3` error counts are compiler output, but many of them are false-positive narrowing, so they measure how much code is untyped rather than how many defects there are.

## Conclusion

These codebases were built carefully, so they do not accumulate problems as clutter. Their weak point is the seam between what the code does and what the documents, contracts and public pages say it does. The ADR-044 contract description, HeroSet's architecture tree, HeroFace's plan and compatibility docs, and the staged site copy all describe a project state that no longer exists, or does not exist yet. The single most useful process change is to tie public copy to the **store upload** it describes rather than to the session that changed the code, and to write that rule into verden-site/CLAUDE.md. On the code side, the pattern across all three projects is to harden the few places where the platform can throw or return null (`updateComplication`, `complicationId`, Storage value types) and to leave the rest alone. Every high-value fix above fits the existing patterns; none replaces them.
