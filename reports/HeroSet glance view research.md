# Ship a read-only glance on 63 watches

HeroSet can get a glance-list entry with **no manifest, permission, storage-key or complication change**, but only on **63 of its 80 products**, and the decision that matters most is not technical. The 63 are every product at Connect IQ (CIQ) 5.0 or newer. The 17 CIQ 3.4 products (fēnix 6 family, MARQ Gen 1, Descent Mk2, FR945 LTE, Enduro) get nothing: the compiler drops the `(:glance)` annotation with a warning and the build still succeeds. The glance has to live inside HeroSet, because a separate widget app cannot see HeroSet's Storage and only watch faces can subscribe to its complication. The research answers the owner's "let research decide" question with **read-only status, no hint text**: one streak line over a row of three pill bars (push-ups, sit-ups, squats), using only strings HeroSet already ships in 15 languages. A measured prototype puts the glance-scoped code at **about 6.9 KB against a 64 KB limit**, and it compiled on all 80 products and passed the existing unit suite plus three new reader tests. The real work is one rewrite of `HeroSetApp` so the glance process never builds the store or publishes the complication, plus scope attributes on strings in 15 language files. Two risks can only be settled on the FR965, and the first should block the upload: an app launched from a glance may be **terminated after a period of inactivity**, which could silently lose an unsaved set; and glance-scope mistakes compile clean at the default build level and fail only at runtime. Version 1.1.1 is already live and `go-to-market.md` says "feature work waits", so the owner must lift that rule and pick a version label (recommendation: 1.1.2, as its own upload). Nothing in the notes ran in glance mode or on a wrist, so every runtime claim below is simulator-adjacent or inferred.

## How to read the evidence

Three grades are used throughout. **Measured** means a build, test or simulator run whose output the research notes reproduce: the compiler experiments on SDK 9.2.0, the 80-product build sweep, the differential and zero-write reader tests, and the font metrics from a stub app ([codebase note](../research_notes/HeroSet%20glance%20view%20research/codebase_fit_and_impact.md), [platform note](../research_notes/HeroSet%20glance%20view%20research/glance_platform_mechanics.md), [design note](../research_notes/HeroSet%20glance%20view%20research/glance_design_and_ux.md)). **Cited** means a statement in the SDK 9.2.0 documentation, the per-device `compiler.json` and `simulator.json` files installed with the SDK, the repo's own docs, or a named forum thread. **Inferred** means my reasoning from those, and each inference is labelled as such. Where sources conflict, the tie-break is: device data beats SDK prose, compiled evidence beats forum claims, and a specific SDK statement beats a general one. The conflicts that matter are collected in a table in the section on risks and unknowns.

One caveat governs the whole report. The simulator's glance mode is a GUI setting that could not be scripted (macOS refused assistive access), so **no glance was ever run in glance mode, and none ran on a device** ([codebase note §8](../research_notes/HeroSet%20glance%20view%20research/codebase_fit_and_impact.md)). The simulator also wedged repeatedly and was killed and restarted twice. That side effect changed coverage, not any reported number: the per-product fit sweep reached only 7 of 63 products (fenix7s and fr265s produced no result), one full-suite re-run and two single-test re-runs were repeated after restart, and the translated-string width run for fr255s printed nothing. Every figure below comes from a run that completed. The static compile numbers were unaffected because they need no simulator.

## The glance must live inside HeroSet, and 63 of 80 watches can show it

**Why inside HeroSet.** On CIQ 4.0 and newer, Garmin says apps can have glances and that "creating a glance for your application gives users two unique ways to launch your app" ([SDK app and system modules][appmods]). Selecting the glance launches the app itself, so the glance is HeroSet's second front door rather than a separate product. A separate widget app fails on data: `Application.Storage` takes only a key, with no app id or scope, and the one documented cross-app channel is Complications, where "only watch faces can subscribe" ([SDK Complications][compl]). The claim that one app cannot read another's Storage is inferred from the API shape, not quoted from a doc, but it agrees with ADR-044's private complication. A widget build would also be the wrong type on the modern watches: on CIQ 4+ a manifest `widget` is built as a watch-app anyway ([Garmin forum bug report][f-3061]), and a `ComplicationPublisher` widget failed to compile in the 4.2 beta ([forum][f-widgetvsapp]). The `glancePreview` complication attribute (4.2.0) is a complement, not a substitute: it only feeds the preview text when a user puts a glance into a glance folder ([SDK Complications][compl]). Call the feature a "glance" in every user-facing string; that is Garmin's current term, and "widget" is the older name.

**Which products.** Cited and measured agree. Watch-app glances arrived in SDK 4.0.0 ([SDK history][history]), and the glance API itself dates from 3.1.0, not 3.3 ([SDK Glances][glances]). On 4.0+ an app "must implement a glance view to appear in the glance list", so today HeroSet is absent from that list on every watch. The per-device data (`compiler.json`, `simulator.json`) gives every one of the 80 products a glance entry, but the Device Reference marks the 17 CIQ 3.4 products "Build as Widget", and HeroSet is a watch-app ([Device data](../research_notes/HeroSet%20glance%20view%20research/device_support_and_memory.md)). The compile experiment settles it: a probe watch-app built for all 80 products succeeded, and exactly those 17 emitted "Glance applications are not supported for app type 'watch-app' on device 'fenix6' … The (:glance) annotation will be ignored" ([platform note §1](../research_notes/HeroSet%20glance%20view%20research/glance_platform_mechanics.md)). The design note compiled only fenix6 and called the other 16 an inference; the later 80-product sweep with the real prototype measured all 17 ([codebase note](../research_notes/HeroSet%20glance%20view%20research/codebase_fit_and_impact.md)), so the sweep is the stronger source.

| Group | Products | Glance limit | Watch-app limit | Live updates | Glance content area |
|---|---|---|---|---|---|
| Gets a glance (CIQ 5.0, 5.1, 5.2, 6.0) | 63 (4 on 5.0, 6 on 5.1, 29 on 5.2, 24 on 6.0) | 64 KB | 768 KB (512 KB on fr255, fr255s) | Yes, all 63 | 140x79 (fr255s) and 151x63 (fenix 7S) up to 359x130 (fēnix 9 Pro 51); Venu 3 is tallest at 303x164 |
| No glance from a watch-app (CIQ 3.4) | 17: fenix6, fenix6s, fenix6pro, fenix6spro, fenix6xpro, 8 MARQ Gen 1, descentmk2, descentmk2s, fr945lte, enduro | 32 KB, unused | 128 KB (fenix6, fenix6s, enduro) or 1280 KB | No on 11, yes on 6; moot | Ignored |

Those limits are device data, not prose. The SDK Glances page says "32KB for most devices"; `compiler.json` says 65,536 bytes on all 63 supported products, so the doc predates the newer watches and the device files win ([SDK Glances][glances]; [fr965 compiler.json][fr965dev]). The doc's "music-capable wearables get live updates" footnote is also contradicted by device data: non-music FR255, FR255s and FR165 have `liveUpdates: true`. That conflict is harmless here because all 63 supported products are live, which removes the cached-render and 30-second-refresh path from the design entirely. Whether a user can hide the glance is a list-customisation matter on CIQ 4+ ([FR965 manual][m-965]), and "some glances are not visible by default" means the owner should not assume the glance appears without the user adding it; that default is undocumented for updates to an installed app.

## What the glance process runs, and what HeroSet must change

**Platform mechanics (cited).** `AppBase.getGlanceView()` returns `[GlanceView]`, `[GlanceView, GlanceViewDelegate]` or null; null shows the app name only, which is the cheapest stepping stone and a useful fallback ([SDK AppBase][getglance]). The glance view is an ordinary `View` on a clipped rectangular `Dc`: `onLayout`, `onShow`, `onUpdate`, `onHide` run; layers and page stacks do not; it takes no input; the delegate is a no-op ("none for now") ([SDK GlanceView][glanceview]). Forum advice on the return shape conflicts (one thread says returning a delegate crashed, another fixed a stale glance by adding one), so **return the view alone**, which is common practice and needs no delegate ([forum][f-delegate]). Storage, Properties, `Time`, `Gregorian`, `getApp()` and glance-scoped resources all compile inside a glance; each Toybox module still needs its own manifest permission ([platform note §2](../research_notes/HeroSet%20glance%20view%20research/glance_platform_mechanics.md)). The launcher icon is drawn by the system beside the content area, so the glance needs no icon resource. On live devices the process is kept alive and redrawn "as needed", with updates advised under 1 Hz ([SDK Glances][glances]). HeroSet needs no timer: totals change only while the user is inside the app, and the list redraws on scroll (inference).

**The one structural change.** The `AppBase` subclass is always loaded whole in the glance process. Measured: adding 60 statements to the body of `AppBase.onStart` grew glance code from 442 to 1,359 bytes, while an unannotated 60-method class left glance code unchanged ([platform note §3](../research_notes/HeroSet%20glance%20view%20research/glance_platform_mechanics.md)). HeroSet's `HeroSetApp.initialize()` builds `HeroSetStore` and `HeroSetSyncCoordinator`, and `onStart()` calls `ensureCurrentDay()` and publishes the complication. The store's constructor writes `hero_schema` every time and can reset the day's counts, so letting it run in the glance process would write from a process the app does not control ([HeroSetStore.mc](../HeroSet/source/data/HeroSetStore.mc)). Two shortcuts were measured and rejected. Annotating nothing makes the compiler load the whole application into the glance ("The entire application will be loaded as a glance process"), 29,778 bytes statically, with the writes and the publish inside it. Tagging the store path costs 7,721 bytes, drags in the learner and swing-trace classes, and still writes from the glance. The design that works, built and run as a prototype: `initialize()` only calls `AppBase.initialize()`; the store and sync coordinator become nullable and lazily created by `getStore()` and `getSync()`; `onStart` is empty; `getInitialView()` performs `ensureCurrentDay()` and the complication publish before returning the view; foreground-only methods carry `:typecheck(disableGlanceCheck)`; and `swapStoreForTest` returns `getStore()` ([codebase note §3](../research_notes/HeroSet%20glance%20view%20research/codebase_fit_and_impact.md)). This moves ADR-044's "app start" publish point to "first view request". The two are the same moment for any real launch, but it must be checked once on the FR965 with HeroFace installed. The glance also cannot tell it is the glance process, since `onStart` receives no such argument (`:launchedFromGlance` marks the foreground launch), so an `onStart` that touches nothing foreground is the only safe shape.

**Memory budgets.** Measured static cost of the whole glance closure (`monkeyc --build-stats`, FR965, store jungle): **6,856 bytes** (data 2,419 plus code 4,437), 6,905 in the dev build, against the 64 KB glance limit, roughly 10 percent. The heavy items are `HeroSetDraw` (1,225 B), `HeroSetLayout` (1,076 B), `HeroSetRules` (813 B) and the two new classes (about 1.15 KB together). The rest of the app grows by about **1,342 bytes (4.5 percent)** in the foreground, which leaves the recorded "dashboard about 52 KB, workout about 54 KB" of the 768 KB watch-app budget untouched ([decisions.md ADR-038](../HeroSet/docs/decisions.md)). What is not measured is peak heap inside the 64 KB glance process, the resource-table cost, and font memory; the unit runner reported 8 MB, so the only heap probes (240 bytes for one reader call) prove almost nothing. A forum thread also warns that simulator peak memory understated real need for a glance that stored JSON ([forum][f-json]). HeroSet reads ten small keys, so the risk is scope errors, not size (inference). Keep the file list small and skip splitting `HeroSetRules` or `HeroSetLayout`; about 1.5 KB of possible savings buys nothing at a 64 KB limit.

**Data freshness and the read-only reader.** The store resets the day lazily, so at 00:01 the stored `hero_pushups` still holds yesterday's count; a glance that read it directly would show yesterday's "mission complete" until the app was opened. The design is therefore a static, read-only `HeroSetGlanceReader.read(storage, today)`: a count counts only when `hero_day == today`, the streak comes from the pure `HeroSetRules.activeStreak`, the goal uses the store's zero-as-unset rule, and nothing is ever written. Measured on the FR965 simulator, with the real store as oracle: `glanceReaderMatchesTheStoreOnTheSameDay`, `glanceReaderNeverWritesAndReadsStaleDaysAsZero` (a counting subclass proves zero `setValue` calls) and `glanceReaderCopesWithMissingCorruptAndFloatValues` all passed, in a full run of 103 tests with no failures. The glance reads on every `onUpdate`, not in `initialize`, because a live glance can outlive midnight or a goal change. One defect to fix: the prototype reader tolerated Float for counts and goal but only `Number` for `hero_last_completion`, unlike the store's `asNumberOrNull`. Torn reads between a writing app and a reading glance are not expected to overlap, and would cost one stale draw (inference; whether the processes can overlap is undocumented). Key spellings (ADR-003) would exist twice; the recommended first step is to keep literals in the reader and let the differential test pin them, deferring a shared constants class to the ADR-020 store split.

## Show the streak and three pill bars, and leave the hint out

**The design decision.** Research resolves the owner's open question to **read-only status**. Store precedent for habit and goal glances is status only (n done, percent with a bar, streak); the one prescriptive glance found ("Challenge Counter") is an outlier ([store listings cited in the design note](../research_notes/HeroSet%20glance%20view%20research/glance_design_and_ux.md)). The hint's content already exists one press away: the main menu opens focused on the first exercise not yet at goal ([input-and-ux.md](../HeroSet/docs/input-and-ux.md)). A text hint would add at least one string in 15 locales whose translations are not native-reviewed ([release-contract.md](../HeroSet/docs/release-contract.md)), and a third text row does not fit the 63 px glances on the fēnix 7 family. The "next exercise" answer rides the pills for free, since exercise order is fixed by ADR-044 and the first pill that is not full is the next one. If a hint is ever wanted, make it a drawn marker on that pill rather than words (inference; untested, and 5 to 8 px pills make clutter likely).

**Layout (inference from measured font heights, not tried on a device).** Row one, in `FONT_GLANCE`: the streak line by longest-first candidates (`N DAY STREAK`, then `STREAK N`, then dropped), with `NO STREAK YET` at zero, muted while today is open and gold once today's mission is complete, exactly as the dashboard does. Row two: three equal pill bars side by side, a track drawn first, fill in the effort blue and a done pill full and green, height about `min(w,h)/10`. When all three are done, row one becomes a drawn check plus `MISSION COMPLETE` if it fits, else the streak text with the check, else the check alone; the full green pills and the check carry "done" without colour or a translatable word (ADR-049). Draw with a transparent background and no `dc.clear()` fill: forum and open-source evidence says an opaque fill paints a flat rectangle over the themed card on FR965, Venu 3, fēnix 8 and others ([forum][f-transp]). The palette is already 64-colour-exact for MIP; the residual risk is contrast, since HeroSet's TRACK grey `#555555` is close to the White theme's card grey `#525252`, so outline the track (measured colour samples, untested on device).

**Why this fits.** The glance area is a rectangle from 140x79 and 151x63 up to about 300x150 on AMOLED, so two `FONT_GLANCE` text lines (about 19 to 22 px each on MIP) plus a thin graphic fit even at 63 px, while three labelled bars do not. The measured strings show the constraint: "MISSION COMPLETE" is 135 px wide at `FONT_GLANCE` on the fr255s's 140 px area, and Polish `MISJA ZAKOŃCZONA` is 146 px on a 171 px fenix 7 area, so the word must be droppable. The prototype's fit test failed on `9999 DAY STREAK` at fr965 (311 px vs 299) and fr165 (262 vs 261), which is the reason for the candidate list and the widest-state convention (9999-day streak, goal 500). Ranked options: three pills plus streak first, combined percent plus streak second (fallback if the pills prove too small on a wrist, needs no new strings), "reps left" third (a new plural-sensitive string), text hint last. No glance with three separate goal bars appeared among about 80 store descriptions read, so the layout is novel, though it mirrors HeroFace's mission columns. The house rule that all text goes through `HeroSetDraw.text` still holds, but `HeroSetLayout` assumes a round chord; the prototype added a three-line `rectangular()` factory, and the pills need their own small horizontal-segment drawer because `HeroSetMissionBars` is chord-based and label-driven. Glance geometry (bar height, gap, small-area threshold) needs named constants, since the dashboard's short-side formulas give 2 px bars and 0 gap at 63 px.

**Edge states.** All map to existing wording, so no new copy is required.

| State | Glance shows | Reason |
|---|---|---|
| Never launched | Three empty tracks, `NO STREAK YET` | Missing keys already read as 0 with default goal 100 |
| Day rolled over, app not opened | Counts 0, streak from `activeStreak`, no write | Otherwise 08:00 shows yesterday's completion |
| Goal changed or lowered | Reads goal every draw; done means count ≥ goal | `setGoal` already re-runs completion in the app |
| Missed a day | `NO STREAK YET` | ADR-031 honest streak, same as dashboard |
| Storage error | Zeros, or empty tracks on a thrown read; no `COULD NOT SAVE` (flag is not persisted) | Reader must never crash |
| 17 CIQ 3.4 products | Nothing | Annotation ignored |

A time-of-day streak-at-risk cue is feasible without the `Background` permission (the glance can read the clock), but v1 does not need one: muted streak plus partial pills already signal it, and there is no evidence for the right hour. If added later, it must not use the words "reminder", "alert" or "notification" and must not rely on colour alone.

Two facts govern the scope annotations. Annotation is class-level: putting `(:glance)` on one function of an unannotated class still pulls the class in (measured). And resources need `scope="glance"`, otherwise a glance touching a foreground resource fails at runtime with "Illegal Access (Out of Bounds)" ([forum][f-illegal]); whether each language file needs the attribute or only the default file is unverified, because scoping only the German file also silenced the lint, so put it in all 15 files (the default plus 14 language folders) and test a second language.

**Tests.** Unit tests cover what the simulator can prove: reader parity with the store on the same day, zero writes, stale-day zero, streak boundaries, goal default and clamp, Float-stored values, `getStore()` builds once, and the widest-state draw. The test count moves from 99 dev and 88 store to about 103 and 91, to be read from `Ran N tests` at implementation time. The per-product fit test has no runtime API for the glance size, so it needs a table of 63 content-area rectangles from `simulator.json`; extend `tools/fit-sweep.sh` for languages. Add the `-l 2` grep as the only pre-device scope guard: `monkeyc … -w -l 2 | grep "not available in all function scopes"` must print nothing. `-l 3` cannot be a blanket gate because the existing code already fails it for unrelated reasons (`HeroSetStore.mc:182`, `HeroSetCalendar.mc:14`, `HeroSetMenuDelegate.mc:24`). Pin the SDK at 9.2.0: releases 8.1.x and 8.3 each had glance-related simulator regressions (8.4.0 fixed the 8.3 macOS crash) ([forum][f-mac]).

**Simulator versus FR965.** The simulator can show the drawing, fit and the dashboard-from-glance flow, using Settings then Glance Launch Mode (renamed from Glance View in 4.1.4; it is greyed out if `getGlanceView` is misspelled, per a 2026 thread ([forum][f-sim])), and can capture a listing screenshot. It cannot prove real glance-process memory or kill behaviour, the refresh cadence, the idle timeout, Storage timing between the two contexts, real fonts, MIP contrast, per-language resource loading, or whether a sideloaded watch-app appears in the glance list. Owner-style device testing (all-day FR965 wear, dev build only, no swaps) needs these checks: the glance appears; a saved set shows on return to the list; 00:01 shows zeros without opening the app; a missed day shows zero streak; selecting the glance opens the dashboard and Back returns to the list; **launch from the glance, start a set and idle 60 to 120 seconds**; launch from the glance with HeroFace installed and confirm the complication updates; read `CIQ_LOG.YAML` after the day for glance-process crashes; compare battery against a no-glance day. Simulator passing is not device proof, the same lesson as ADR-046/047, where 1.0.0 shipped with a watchdog crash the simulator never showed ([decisions.md](../HeroSet/docs/decisions.md)).

**Docs, listing and site.** Same-session updates under the repo rules: a new ADR-051 plus an amendment note on ADR-044; `architecture.md` (tree, glance-process rule, read path); `compatibility.md` (63 of 80, the 17 excluded, date bump); `release-contract.md` (a glance row and forbidden claims: glance on every watch, "reminder" or "alert" wording, any claim beyond simulator until a wrist check); `input-and-ux.md` (a Glance section; Back from a glance-launched dashboard returns to the glance list); `ideas.md` idea 1 graduates; `go-to-market.md`, `testing-plan.md`, `development.md` (the `-l 2` step); `CHANGELOG.md`; `listing/README.md` with a paste-ready What's New block (the previous block moves to `listing/NOTES.md`) and the App Version bump; and repo-root `TODO.md`. The test count is written in four places: `CLAUDE.md:18`, `README.md:22`, `development.md:37` and `go-to-market.md:10`. The rule in `CLAUDE.md` still names `release-contract.md` in place of `go-to-market.md`, which is stale by one. On the site, `Support.tsx` gets an FAQ line on which watches have the glance and `Landing.tsx` may get a feature line; `Privacy.tsx` needs no change (no new data, permission or network use), and no published URL changes. ## Risks, unknowns and where sources disagree

**The idle timeout (ship-blocking).** The SDK says: "If an app is launched from the glance list, a timeout will be applied to the app. If the user does not exit the app within a given time frame, the system will terminate the app and return to the home screen. If an app is launched from the activity menu, however, it will not time out" ([SDK app and system modules][appmods]; the same rule appears in [Entry Points][entry]). HeroSet is the worst-case app for this: a user starts a set, does reps for a minute without touching a button, and `battery.md` already records that if the system times the app out, "an unsaved set is silently lost" ([battery.md](../HeroSet/docs/battery.md)). No source gives the duration or says whether accelerometer activity or rep detection resets the timer. This is a conflict inside the sources: the SDK's UX guidance says "Device apps are launchable experiences that do not time out" ([Developing the Concepts][concepts]), and one forum poster says Edge devices do not time out, while others say watches do ([forum][f-input]). The specific launch-from-glance sentence is stronger than the general device-app one, but both are prose, not device data, so the question stays open until the FR965 idle test. Mitigations exist only in-app (persisting the running set count, or branching on `:launchedFromGlance` in `onStart`), and either is a separate ADR. A related inference: the same forum says a glance-launched app cannot record an activity, which matters for the planned 1.2.0 Connect sync (ADR-043), so test "launch from glance, set with sync on, save" before combining the two.

**Silent scope errors.** At the default build, and at `-l 1`, a `(:glance)` path that calls foreground code compiles with `BUILD SUCCESSFUL`; the check exists only at `-l 2` (warning) and `-l 3` (error). With `(:glance)` on `HeroSetApp` and the original body, `-l 2` flagged `HeroSetStore`, `HeroSetSyncCoordinator`, `ensureCurrentDay`, `HeroSetComplicationPublisher`, `stop`, `HeroSetView` and `HeroSetDelegate`; the compiler treats `AppBase` methods as glance-visible code (measured). The compiler also cannot tell which annotated code actually executes in the glance, so reachability from `initialize`, `onStart`, `onStop`, `getGlanceView` and `onUpdate` needs a review checklist item. Real-world failures look the same: "Illegal Access (Out of Bounds)" from a resource reference in a class variable initialiser, with a stack trace pointing elsewhere ([forum][f-illegal]). Memory overrun is only a warning since SDK 4.0.0, and the 2019 fēnix 6 reset loop that appeared only on device ([forum][f-reset]) is the same shape as HeroSet's device-only 1.0.0 watchdog crash. None of the 32 KB fēnix 6 anecdotes applies here, since those products get no glance.

**Other risks.** Firmware behaviour is not simulated: a glance can flash a grey rectangle with the app name for one to two seconds before drawing on fēnix 8 ([forum][f-render]), and 2026 reports of glance order resetting after a sync are secondary aggregator reports ([the5krunner][f-order]). Where the simulator and hardware differ on glance size, the notes cannot say; the simulator's `contentArea` matches Garmin's own 151/171/191 x 63 numbers for the fēnix 6 family, which supports treating it as the dc size (inference). On round bezels a developer reports clipped left edges of titles inside fēnix 8 glances ([trainbud source comment][f-trainbud]), so keep top, bottom and left padding. Garmin's review of a new app-type behaviour is not documented anywhere the research reached; no permission changes, so expect a normal review, but the 1.0.0 exposure lesson argues for a rollback build ready in the first week.

## Release and versioning

The repo forces an owner call here. `go-to-market.md` line 5 says "Feature work waits unless it unblocks a fix", and 1.1.1 went live on 2026-09-24, so the glance cannot ride 1.1.1; ADR-050's "next upload is 1.1.1" is history, and the listing file names 1.2.0 (Connect sync) as next ([go-to-market.md](../HeroSet/docs/go-to-market.md), [listing/README.md](../HeroSet/listing/README.md)). The recommendation is to ship the glance as **its own upload, 1.1.2, after the owner lifts the rule and the FR965 checks pass**. The reasons: the glance adds no permission, storage key, complication or manifest change, so it is the lowest-review-risk feature waiting; bundling it into 1.2.0 would tie it to sync's Fit and FitContributor permissions and a ten-item device acceptance measured in weeks; and a first release of a new process type is safer isolated so any failure is attributable and the rollback build is obvious. The cost is a patch number on a feature. The clean-semver alternative, 1.2.0 for the glance and 1.3.0 for sync, rewrites references in ADR-043, ADR-047, ADR-050, `connect-sync-plan.md`, `ideas.md` and `go-to-market.md`. The version lives only in the store form (ADR-047), so this is an owner decision. Whichever it is, the repo rule for every store publication applies: a `CHANGELOG.md` entry, a paste-ready What's New block, the previous block moved to `listing/NOTES.md`, and an App Version bump. Listing copy may say the glance shows streak and progress on 63 watches; it must not say reminder or alert, must not claim all 80 watches, and must say simulator-only evidence until a wrist check passes.

## Conclusion

The research reframes the request. The glance is cheap in bytes and design, and the expensive part is process hygiene: it forces HeroSet's app class to stop assuming the store exists, because the glance process loads that class whether or not the design wants it. A read-only reader tested against the real store as an oracle turns the two quiet failure modes, key drift and accidental writes, into test failures instead of field reports. That leaves the risk on the launch path, not the glance: Garmin documents that an app launched from a glance times out on inactivity, and HeroSet is a workout app that waits for reps, so the feature's downside lands on the paid product's core flow.

The measurement gap matters as much as the design. Every runtime question, including memory in the 64 KB process, timeout length, the refresh cadence, real fonts and per-language resource loading, is unmeasured because no glance has run outside the compiler and unit runner. The build evidence is strong (80 of 80 products build, 63 carry the glance, 103 tests pass), the device evidence is nil, and the owner's usual all-day dev-build wear on the FR965 is the right instrument.
